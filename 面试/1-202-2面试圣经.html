    项目问题二：Jenkins CI/CD

    持续集成(CI)：开发人员写好代码后，需要提交到代码库合并，进行代码的编译和自动化测试。通过工具使得代码的编译和自动化测试工作能够自动进行，并发布到测试环境中，这个过程就叫做持续集成。持续交付(CD)：发布到测试环境，由测试人员测试通过后，发布到生产环境，这个过程叫做持续交付。持续部署(CD)：如果CI后不需要人干预，软件的测试以及发布全部自动完成，这个过程就叫做持续部署。Jenkins是一个常见的CI工具，常见的CI/CD工作流程一般为：开发人员将代码提交到github代码仓库中，jenkins定期检测代码库中对应的分支是否更新（或者分支更新后通知jenkins拉取分支），如果更新就执行对应的构建脚本(包括：编译代码、执行自动化测试、打包成镜像发布到镜像仓库中，先拉取到测试环境中，由测试人员测试，测试通过后发布到生产环境)】。

    项目问题七：在项目中，遇到的bug

    在测试用户管理模块时，发现点击修改某些用户状态无反应。怀疑数据库外键问题，检查后排除，发现其他用户可以修改，不能修改的用户修改昵称后可成功删除，通过查看操作日志发现，后端代码是根据昵称修改，用 “等于” 条件执行update语句，遇到同名用户情况会修改多条数据，由于后续会根据修改数量进行判断，当修改数据数量不为1时，说明出现问题，事物回滚，导致修改失败。最终开发将前端传参改为传用户 ID来进行修复。

    项目问题九：公司接口数量，接口自动化覆盖率
    • 自动化测试的目的是降本增效，公司接口测试用例的数量为400，接口自动化的覆盖率一般在90%+。
    • 在多个接口进行自动化测试的时候，会出现网络抖动的问题【接口越多，越容易出现】 --> 出现少数几个接口返回时间长。
    • 应对方案：可以使用超时-重试机制。超时机制可以解决系统的效率问题，一般如果3s没有返回结果，就认为超时，超时的接口本身就是不合格的。重试机制可以保证系统的质量问题，可以设置重试4次，每次等待1秒。
    • PS：框架运行时，一个接口报错不会影响下一个接口继续测试。
    项目问题十：接口自动化覆盖率达到了多少？为什么能那么高？

    400多条接口测试用例，覆盖率达到了90%以上。我们是基于自动化测试框架的excel模板去编写测试用例的，一般来说测试用例编写完毕，就可以提供给自动化测试框架进行使用。其中，有一部分接口测试用例没有实现接口自动化，比如：一些人机交互的场景（验证码验证：自动化测试框架没有办法很好地做到）以及一些临时的活动页面。

    项目问题十一：说说你们公司的整个自动化测试流程

    我们是基于python实现的自动化测试框架来实现自动化测试的，我们只需要按照要求去编写测试用例，就能实现自动化，不需要自己手动编写代码。

    一般流程：

    • 当需求评审结束后，前后端人员会编写对应的接口设计文档，根据这些文档我们可以进行初步的测试用例设计。
    • 我们会基于测试框架对应的yaml模板进行测试用例的初步编写，编写完毕后我们会进行初步的评审。因为此时接口后端还没有开发完，可能会进行变动。
    • 等后端人员开发完毕后，我们先使用postman测试工具自测一遍，测试通过后，结合接口文档以及postman的测试脚本完善之前测试用例，把接口需要的参数、请求方式给完善起来。
    • 写完测试用例，我们会在自己的电脑上跑一遍测试用例，如果没问题就将编写的yaml用例提交到git上面。
    • 使用jenkins实现每日的回归测试，以及代码提交后的自动测试。
    • 测试如果出现问题，会通过机器人发送到对应的钉钉群里。
    补充：
公司开发的python + pytest + requests框架集成到git中，这个框架可以读取对应yaml中的测试用例，实现自动化测试。我将编写的yaml用例也上传到git中，一旦jenkins监测到对应的代码发生变动，就会进行自动化测试。
可以配合持续部署一起使用，将测试完毕的程序，打包成新的镜像，添加到镜像仓库中。
    项目问题十二：说一下 python + request + pytest 框架的设计思路

    该框架主要包含公共模块、测试用例模块、测试数据模式和配置模块：公共模块基于关键字驱动设计，封装公共服务（如 HTTP 请求、数据处理）；测试用例模块负责编写具体测试逻辑；测试数据模块遵循数据驱动模式，将测试数据与测试用例分离，测试数据以.yaml 格式存储，支持单个用例执行多组数据；配置模块读取.ini 格式的配置文件以获取环境信息等。框架通过断言处理响应结果，并利用 pytest 夹具机制实现数据关联，例如在测试用例类执行前获取 token，确保测试流程的动态依赖和状态传递。

    Note：
1. 关键字驱动模式：将操作行为封装成函数或者方法。通过调用函数或方法来实现对操作行为的调用。可以基于操作行为进行封装，也可以基于业务进行封装。
2. 数据驱动模式：将测试数据与测试逻辑分离，通过配置文件或者数据库存储测试数据，让同一套测试逻辑可以执行多个测试数据。
3. token的获取：一般都是先查看有没有对应的文件，如果有从中获取token数据。如果没有就请求后端获取token，创建对应的文件，将token存储在里面，方便下次获取。
    项目问题十三：selenium项目如何搭建

    搭建一个selenium项目【主要通过webdriver中间服务来与浏览器交互】可以主要分为四个模块：一个是common公共模块，来对一些公共操作进行封装，比如日志操作、数据库操作以及针对元素的一些操作（点击、获取值）。包含一个config配置模块，来获取和定义对应的配置信息，比如数据库的相关信息以及URL地址等配置信息。包含一个po页面对象模块，一个页面对应一个页面对象，来封装对于不同页面的操作（如登录功能进行封装）。然后测试用例模块用来编写我们的测试用例，可以使用断言来检查是否能够返回正确的操作结果，配合pytest的夹具来定义前置、后置的操作，配合allure生成测试报告。【对于不同浏览器的适配性测试】

    固定等待：全局暂停，不针对任何元素，效率低，不推荐。
隐式等待：针对所有元素，统一设置等待时间，适用于简单场景。
显式等待：针对特定元素，灵活设置查找等待时间，适用于复杂场景，推荐使用。

    好处：高内聚、低耦合。

    项目问题二十二：前端及后端的单独测试，联合测试怎么做？

    前端测试主要包括：

    • 单元测试：验证单个组件的渲染效果、对应功能是否正常，如：提交按钮在点击提交时，能提交表单。
    • 集成测试：验证多个组件的交互是否正常，如：点赞功能，点击点赞按钮后，点赞数+1。
    • 端到端测试（E2E）：模拟真实用户操作，如：登录 -> 浏览商品 -> 添加到购物车，测试在整个业务流程中前端的显示是否正常。

    java中的两把锁：Synchronized和ReentrantLock【可以实现并发场景下的互斥同步】

    是并发编程下保持线程同步的重要手段，Synchronized可以用来锁住方法，锁住代码段，支持可重入，满足低并发场景下的应用。如果需要对锁进行精细化的控制，比如：超时获取锁（获取锁时，设置一个超时时间）、避免一个线程长时间占用锁，需要使用支持超时机制的reentrantlock，reentrantlock还支持公平性的选择。synchronized会在释放锁的时候，随机选择一个线程去获取锁。reentrantlock采用公平性的选择，排队来获取锁。如果需要在高并发场景下，实现锁的精细化控制，最好使用reentrantlock。

    引用拷贝、深拷贝和浅拷贝

    引用拷贝只是复制对象的地址，新旧变量指向同一对象；浅拷贝在堆中创建新对象，复制基本数据类型以及引用对象的地址；而深拷贝不仅会复制基本数据类型，还会创建引用对象的完整副本，完全实现新旧对象的隔离，性能开销最大。

    接口和抽象类的区别：

    语法层面：

    • 抽象类可以提供成员方法的具体实现，接口的方法必须被public abstract修饰。
    • 抽象类成员变量可以是各种类型，接口的成员变量要被public static final修饰。【静态类型属于类，而不是属于类的实例】
    • 抽象类可以使用静态代码块，接口不能使用静态代码块。【静态代码块，类加载到JVM虚拟机中调用一次】
    • 一个类只能继承一个抽象类，一个类可以实现多个接口。

    理解层面：

    接口是对事物的抽象描述，只描述事物的共性，比如：有一个眼睛、一个嘴巴，可以说话，可以吃饭。但并不提供行为的具体细节。而类的话是对事务的具体描述，定义了它如何说话，如何吃饭。抽象类位于类的具体和接口的抽象之间，可以提供一些具体的行为。

    Note：

    抽象类和类的区别：抽象类不能直接实例化，类可以直接实例化。

    实现单例设计模式

    饿汉式：

    public class Singleton {
    // 类加载时就创建实例，天生线程安全
    private static final Singleton instance = new Singleton();

    private Singleton() {} // 私有构造方法，防止外部 new

    public static Singleton getInstance() {
        return instance;
    }
}

    懒汉式：

    public class Singleton {
    // volatile 防止指令重排
    private static volatile Singleton instance;

    private Singleton() {}

    public static Singleton getInstance() {
        if (instance == null) { // 第一次检查，减少锁竞争
            synchronized (Singleton.class) {
                if (instance == null) { // 第二次检查，确保只有一个实例
                    instance = new Singleton();
                }
            }
        }
        return instance;
    }
}

    面向过程和面向对象

    面向过程是指将一组行为或者事件封装成多个函数，通过函数的调用来完成特定的事件。面向对象是指将一个事件或者一个事物封装成一个类，通过实例化类调用对象中的方法或者属性，来完成特定事件。

    面向对象的特点

    封装、继承、多态。封装是通过使用访问修饰符（如private）来隐藏对象的内部状态，外部只能通过一些公共的方法去访问；继承是通过子类继承父类的属性和方法来实现代码复用；多态是通过方法的重载、覆盖和接口多态来实现同一个操作作用于不同的对象时可以有不同的执行结果。

    String、StringBuffer、StringBuilder的区别
    // 下面的情况，会先检查常量池中存不存在对应的数据，如果不存在就会创建，否则就不创建。
String a = "a";
String b = "a" + "b";  // 编译阶段写成"ab"

// 下面的情况不光会在常量池中创建，还会在堆中创建
String a = new String("ab");

// 在常量池中创建
String b = "x"; 
// 不光在常量池中创建，还会在堆中创建
String b = b + "a";

    String对象是不可变的，每次改变本质上都是在堆中创建一个新的对象。StringBuffer和StringBuilder的对象是可变的，通过内部维护一个动态字符数组来实现。其中，String和StringBuffer是线程安全的，StringBuffer通过synchronized关键字进行修饰、String利用自身的不可变特性；StringBuilder不是线程安全的。

    补充：

    StringBuffer是对方法使用syncronized关键字进行加锁。

    String保证不变性：使用final类修饰String类，防止其它类继承。使用private final修饰字符数组，保证字符数组私有，无法指向其它数组，每一次修改字符数组都会创建新的对象。

    SPI服务提供接口

    提供了一种服务发现的方式。主要由三部分组成Service(服务：接口或者抽象类)、Service Provider(服务提供类：实现对应的接口或者抽象类)、Service Loader(服务加载类：加载服务实现类)。可以将服务、服务实现类、服务加载类分别打包成不同的JAR包。服务实现类使用META-INF/services/接口全限定名(包名 + 类名)来命名配置文件，文件内容为实现类的全限定名。通过使用服务加载类的load方法，程序就会从ClassPath路径下找到所有名为META-INF/services/接口全限定名对应的配置文件【不用关心后缀名】，读取文件内容，根据类名来加载实现类数据。

    使用场景：JDBC驱动，java通过SPI来加载不同的数据库驱动（Mysql、Oracle）。

    代理模式

    定义：代理模式是通过设置一个代理类来限制程序对目标类的访问，程序只能通过代理类来访问目标类。

    静态代理和动态代理的区别：代理模式分为动态代理和静态代理，静态代理在编译时生成代理类的字节码数据，在运行时通过类加载器添加到JVM虚拟机中。而动态代理是在运行时生成代理类的字节码数据，在运行时通过类加载器添加到JVM虚拟机中。

    动态代理的好处：动态代理可以适用于所有实现一个接口的类，相较于静态代理灵活性更强。

    JDK动态代理

    基于JDK的动态代理：在jdk中，有一个操作类叫Proxy，有个newProxyInstance方法来生成代理对象。这个方法由三个参数组成：类加载器、接口的集合、代理拦截器。

    • 类加载器：将代理类的字节码数据加载到jvm虚拟机。
    • 接口的集合：指示代理哪一个接口，JDK只能基于接口去代理。
    • 代理拦截器：。代理的本质上是执行invoke方法，invoke方法中利用反射机制执行对应的目标方法，然后执行增强的逻辑，实现的目标方法的增强。

    适配器模式：

    适配器模式主要是解决一个类和一个接口不兼容的问题，主要分为目标接口、适配者类以及适配器，通过适配器来实现目标接口与适配者类之间的关联。主要分为类适配器以及对象适配器。类适配器通过继承适配者类，实现目标接口来实现；对象适配器通过实现目标接口，引用适配者类的对象来实现，

    // 目标接口
interface Target {
    void request();
}

// 适配者类
class Adaptee {
    public void specificRequest() {
        System.out.println("适配者的特定请求");
    }
}

// 类适配器（继承Adaptee并实现Target接口）
class ClassAdapter extends Adaptee implements Target {
    @Override
    public void request() {
        specificRequest(); // 调用适配者的方法
    }
}

// 客户端
public class Client {
    public static void main(String[] args) {
        Target target = new ClassAdapter();
        target.request(); // 输出：适配者的特定请求
    }
}

    // 目标接口（同上）
interface Target {
    void request();
}

// 适配者类（同上）
class Adaptee {
    public void specificRequest() {
        System.out.println("适配者的特定请求");
    }
}

// 对象适配器（持有Adaptee的引用）
class ObjectAdapter implements Target {
    private Adaptee adaptee;

    public ObjectAdapter(Adaptee adaptee) {
        this.adaptee = adaptee;
    }

    @Override
    public void request() {
        adaptee.specificRequest(); // 委托给适配者
    }
}

// 客户端
public class Client {
    public static void main(String[] args) {
        Adaptee adaptee = new Adaptee();
        Target target = new ObjectAdapter(adaptee);
        target.request(); // 输出：适配者的特定请求
    }
}

    观察者模式：

    又称发布-订阅模式，分为主题接口、具体主题【包含观察者列表，主题状态改变时调用观察者对应的方法】、观察者接口以及具体观察者。观察者对主题进行订阅，当主题状态发生改变时，会通知对应的观察者，并进行对应的更新操作。

    // 观察者接口
interface Observer {
    void update(String message);
}

// 主题接口
interface Subject {
    void registerObserver(Observer observer);
    void removeObserver(Observer observer);
    void notifyObservers();
}

// 具体主题
class NewsAgency implements Subject {
    private List<Observer> observers = new ArrayList<>();
    private String latestNews;

    @Override
    public void registerObserver(Observer observer) {
        observers.add(observer);
    }

    @Override
    public void removeObserver(Observer observer) {
        observers.remove(observer);
    }

    @Override
    public void notifyObservers() {
        for (Observer observer : observers) {
            observer.update(latestNews);
        }
    }

    public void setNews(String news) {
        this.latestNews = news;
        notifyObservers();
    }
}

// 具体观察者
class NewsChannel implements Observer {
    private String news;

    @Override
    public void update(String message) {
        this.news = message;
        display();
    }

    public void display() {
        System.out.println("收到新闻: " + news);
    }
}

// 测试类
public class ObserverPatternDemo {
    public static void main(String[] args) {
        NewsAgency newsAgency = new NewsAgency();
        NewsChannel channel1 = new NewsChannel();
        NewsChannel channel2 = new NewsChannel();

        // 注册观察者
        newsAgency.registerObserver(channel1);
        newsAgency.registerObserver(channel2);

        // 发布新闻
        newsAgency.setNews("重大新闻：新的设计模式教程发布了！");

        // 移除一个观察者
        newsAgency.removeObserver(channel2);

        // 发布另一条新闻
        newsAgency.setNews("更新：观察者模式示例已完善。");
    }
}
    volatile关键字

    与syncronized之类的重锁不同，volatile是一种轻量级的同步机制，可以保证线程间的可见性。在java内存模型（一个抽象的概念）中，分为主内存和工作内存，共享变量一般存储在主内存中，是所有线程共享的。工作内存是每个线程独有的，当操作共享变量时，会先将变量的副本保存到工作内存中，操作完毕后在填写到共享内存中。而volaitle的可见性让线程在操作完毕后强制刷新主内存，读取时会直接从主内存中进行读取【本质上是通过内存屏障实现的，在写操作之后加入StoreStore屏障，保证在所有写操作完成后，才将变量同步到主内存中；在读操作之前加入LoadLoad屏障，保证在读取前，从主内存中加载最新的数据】。为了进一步防止数据冲突问题，volatile禁止重排序，保证每个"操作"是按照先后顺序来执行的，但是volatile只能保证原子操作的一个同步，如果进行a++之类的操作（分为三个步骤：读取值、a+1、赋值）是无法保证数据的同步。

    CAS

    CAS(compare and swap)是一种无锁机制，当线程对变量进行修改时，会比较变量当前值与线程持有的期望值是否一致，如果一致就执行修改操作。但是可能会导致ABA（线程值 A -> B -> A）问题，为解决该问题也可以使用时间戳或者版本号来判断当前值是否发生更改。

    自旋锁

    与syncronized和reentrantlock这种传统锁机制不同，自选锁不会将线程阻塞，而是让线程不断循环去获取锁的状态，一旦发现锁释放，就立即获取锁，避免了线程启动所造成的延迟。

    Note：

    互斥锁：同时只允许一个线程占用该锁，其它线程想要占有该锁，会被阻塞，直到锁的释放。

    互斥锁和自旋锁的使用场景：互斥锁适用于线程多、占有锁的时间长的情况，乐观锁适用于线程少、占有锁的时间短的情况。如果在线程多、占有锁的时间长的情况下使用乐观锁，会导致有很多线程处于循环等待的状态，导致系统资源的消耗。

    hashMap的实现原理：

    hashMap主要通过数组+链表+红黑树的方式进行实现，当元素放入hashMap中，会通过键对应的哈希值和（数组长度）进行取余运算来求出数组中对应的存储位置，在数组中一开始通过链表的方式进行存储，当链表长度超过8时，使用红黑树的方式进行存储。hashMap默认的数组长度为16，如果hashMap中的元素个数超过阈值（数组长度 * 扩容因子），就会进行数组的扩容操作，一般都是通过当前数组长度*2来进行扩容。

    concurrenthashmap是如何保证线程安全的：

    在JDK(java开发工具包)1.7中，对于写操作concurrentHashMap采用分段锁来保证写操作的线程安全(Reentrantlock)，在JDK1.8中，对于空的槽使用CAS操作来保证线程安全，对于非空的槽，使用槽锁(syncronized，在JDK1.8之后已经通过偏向锁、轻量级锁进行优化)来保证线程安全。对于读操作，是通过volatile关键字，保证线程安全。

    HashTable和HashMap的区别：

    hashMap不是线程安全的，它的键和值都可以设置为null。hashTable是线程安全的，它的键和值都不可以设置为null。当需要保证线程安全时，最好使用concurrentHashMap，而不是hashTable。因为hashTable对于操作都使用syncronized关键字修饰，比较笨重。相比之下，concurrentHashMap可以在保证线程安全的基础上，更加的高效。

    串行、并行、并发

    串行：只有一个CPU，在同一时间段内只能执行一个任务。

    并行：有多个CPU，在同一时刻可以同时执行多个任务。

    并发：只有一个CPU，但是CPU可以分成多个时间片，可以让多个任务在同一时间段内交替执行，但是本质上还是同一时刻只能执行一个任务。

    并发编程的三大特性

    原子性：一个操作或一组操作不可分割，不可中断。同一时刻只有一个线程能执行该操作，其他线程需等待其完成才能开始。【使用syncronized关键字】

    可见性：当一个线程对共享变量进行修改后，其他线程可以立刻看到。【使用volailte关键字或者syncronized关键字】

    有序性：编译后的java代码会转换成CPU可以识别的指令，保证CPU按照指令的先后顺序去执行。【使用volailte关键字】

    PS：可见性问题是指当前线程操作的共享变量值不是最新值。

    syncronized关键字

    syncronized关键字可以实现什么类型的锁？

    悲观锁（当一个线程获取锁后，其它线程必须等待锁释放后才能执行）、可重入锁（同一线程可以重复获取自己持有的锁）以及非公平锁（优先排队的线程不一定能优先执行）。

    syncronized的使用方式

    synchronized 用在普通方法上时，上锁的是执行这个方法的对象[确保对象无法在执行其他同步方法]。

    public synchronized void increment() {
    this.count++;
}

    synchronized 用在静态方法上时，上锁的是这个类的 Class 对象（描述类信息的对象）。

    public static synchronized void increment() {
    count++;
}

    synchronized 用在代码块上时，上锁的是括号中指定的对象，比如说当前对象 this。

    public void increment() {
    synchronized (this) {
        this.count++;
    }
}

    syncronized关键字的实现原理

    本质上是通过JVM虚拟机中的monitor机制（锁）来实现的，每个对象都有与它对应的monitor，monitor一次只能被一个线程获取。将monitorenter指令插入到编译后同步代码块的开始位置，将monitorexit指令插入到编译后同步代码块的结束或异常位置。当一个线程尝试获取monitor时，如果计数器为0，代表当前monitor尚未被获取，线程可以立即获取monitor，将计数器值+1。如果其它线程又想获取锁，就会进行entrylist等待，直到线程释放锁。如果获取锁的线程，想要重入这把锁，计数器就会累加。

    syncronized关键字如何保证可见性和有序性

    可见性：通过monitor机制实现，读取时强制从主内存中读取共享变量，完成修改时强制将修改共享变量同步到主内存中。

    有序性：通过monitorenter和monitorexit指令防止同步代码块中的代码重排序来实现的。

    syncronized怎么实现可重入的

    主要是通过对象头中的markword实现，它可以存储对象状态以及锁的信息，当一个线程获取锁时，JVM会将线程ID写入到markword中，当一个线程尝试获取已持有的锁时，JVM会检查markword中的线程ID，看是否一致，如果一致就将计数器+1。

    锁的升级过程

    无锁->偏向锁->轻量级锁->重量级锁

    ① 偏向锁：用于无竞争场景，当一个线程第一次获取锁时，JVM 会在对象头的 Mark Word 记录这个线程 ID，当再次获取这个持有的锁时，无需额外加锁。

    ② 轻量级锁：当多个线程尝试获取锁但不是同一个时段，偏向锁会升级为轻量级锁，等待锁的线程通过 CAS 自旋（不断尝试CAS操作，直到成功为止）避免进入阻塞状态。

    ③ 重量级锁：如果自旋超过预定次数，锁会从轻量级锁升级为重量级锁，等待锁的线程会进入阻塞状态。

    syncronized关键字和lock接口的区别

    对比维度 **synchronized**关键字 **Lock** 接口(如 **ReentrantLock**是Lock接口的实现)
    加锁方式 自动加锁与释放（JVM 隐式管理） 手动加锁与释放（需显式调用 lock()和 unlock()）
    中断支持 不支持中断（线程必须等待锁释放） 支持中断（通过 lockInterruptibly() 响应中断）
    公平性 仅支持非公平锁 可配置公平锁（new ReentrantLock(true)）或非公平锁
    超时机制 不支持（线程可能永久阻塞） 支持超时（tryLock(timeout)）
    ThreadLocal

    ThreadLocal是什么？

    ThreadLocal是一种线程本地存储机制，可以将数据缓存到每个线程内部。

    ThreadLocal实现原理？

    本质上是通过ThreadLocalMap实现的，每个线程都存在一个ThreadLocalMap，Map中entry对象的key存储ThreadLocal对象，value为需要缓存的值。

    需要注意的问题

    在线程池中使用ThreadLocal对象可能会造成内存泄漏，因为线程池中的核心线程不会回收，且核心线程强引用ThreadLocalMap对象，而ThreadLocalMap对象强引用【强引用对象不会被JVM主动回收，弱引用对象会被JVM垃圾回收机制主动回收】entry对象，所以如果线程不会回收，entry对象也不会被回收，从而出现内存泄漏，解决方法就是使用ThreadLocal的remove方法进行手动回收entry对象。

    使用场景

    线程封闭：数据存储在每个线程中，实现线程间数据的隔离。

    线程池

    使用线程池的好处

    线程池会设置一个线程空闲时间，如果超过这个线程空闲时间，就销毁该线程，否则线程不会被销毁。在线程池中，还可以设置最大线程数以及最大核心线程数，在默认情况下，核心线程不会被销毁，如果有任务会优先分配给核心线程进行执行。这样可以保证在有任务执行时，空闲的线程能够快速响应，而无需等待线程创建所带来的延迟。此外，线程的生命周期由线程池进行管理，无需程序员手动进行管理。最后，线程池可以提供任务队列用来存储需要执行的任务，可以根据任务的优先级来调整任务执行顺序（通过优先级队列实现，重写comparable的compareTo方法）。【线程池中的线程分为核心线程和临时线程】

    线程池的工作原理

    线程池对应的参数包含最大线程数、核心线程数、最大空闲时间、任务队列以及拒绝策略。一开始线程池包含的线程数为核心线程数，如果核心线程都在处理任务，且任务队列中的任务已满，线程池就会创建临时线程用来处理任务【受到最大空闲时间约束】；如果任务队列已满，且线程都在处理任务，就会执行对应的拒绝策略，拒绝执行任务。

    线程创建的两种方式

    使用Executors工具类创建、使用ThreadPoolExecutor完全手动创建。使用Executors工具类创建线程会造成OOM异常。【比如：使用newFixedThreadPool来创建线程池，默认使用无界队列，会导致任务堆积而造成OOM异常】

    线程池的拒绝策略有哪些

    **AbortPolicy：直接抛出异常。**

    **CallerRunsPolicy：由提交任务的线程执行（如：main线程）。**

    **DiscardPolicy：直接丢弃任务。**

    **DiscardOldestPolicy：丢弃任务队列中最老的任务。**

    **自定义拒绝策略。**

    如何给线程池中的线程命名

    使用ThreadFactory来定义线程池中的线程名称。

    最大线程数和核心线程数如何设置

    CPU密集型：核心线程数 = CPU核数

    IO密集型：核心线程数 = CPU核数 * 2

    AQS抽象队列同步器

    AQS 作为 ReentrantLock 等同步器的底层框架，核心由三部分组成：state 状态变量、exclusiveOwnerThread 独占线程标记、双向链表队列。

    其加解锁流程可拆解为：

    加锁逻辑：

    1. 线程 1 获取锁：
    2. 判断state==0，通过 CAS 原子操作将state从 0 改为 1
    3. 设置exclusiveOwnerThread=线程1，成功获取锁
    4. 线程 2 获取锁：
    5. 判断state1，进一步检查exclusiveOwnerThread线程2
    6. 可重入场景： 若是当前线程（如线程 1 重入），则state++（无需 CAS）
    7. 竞争场景： 若不是当前线程（如线程 2），则： a) 创建新 Node 节点（thread=线程2）加入队列尾部；b) 通过LockSupport.park()阻塞当前线程

    解锁逻辑：

    1. 线程 1 释放锁：
    2. 将state--，若递减后state==0（完全释放）
    3. 设置exclusiveOwnerThread=null
    4. 通过LockSupport.unpark()唤醒头节点的后继节点（如线程 2）
    5. 线程 2 被唤醒后：
    6. 通过 CAS 尝试将state从 0 改为 1
    7. 成功后设置exclusiveOwnerThread=线程2
    8. 将自身节点设为新头节点（原头节点出队，等待 GC 回收）

    jvm相关知识

    jvm内存区域

    定义：

    • jvm虚拟机运行时管理的内存空间。

    组成：

    • 堆、栈(分为虚拟机栈和本地方法栈)、程序计数器、方法区。
    • 堆用来存放new出来的对象实例；堆被所有线程共享，它的访问不是线程安全的【一般通过锁机制来解决】；如果堆中的对象超出内存无法回收，就会出现OOM异常。
    • 每个线程在运行时，都有一个独立的栈；栈中的数据是线程私有的，是线程安全的。线程在每次方法调用时，都会创建一个栈帧，用来存储方法运行时的数据(基本数据类型以及对象引用)【虚拟机栈和方法栈的区别在于虚拟机栈主要用来管理java语言编写的方法，本地方法栈用来管理Native方法(C++等底层语言编写)】。
    • 方法区被所有线程共享，存储常量池、静态变量、类的元数据(类的结构信息)和类的字节码数据【.java文件编译后成为.class文件】。
    • 每个线程都有一个独立的程序计数器，指向当前字节码执行的位置，用于控制线程的执行流程。

    Note：

    JDK1.7及以前方法区的实现方式为永久代(属于JVM内存)，常量池和静态变量一般存储在永久代中，到后面JDK1.8之后方法区的实现方式被元空间替代，常量池和静态变量存储在堆中，类的元数据和类的字节码数据存储在元空间(使用本地内存)中。

    GC垃圾回收器

    GC Roots可达性分析 --> 一般被虚拟机栈、本地方法栈、常量或者静态变量直接引用或者间接引用的对象不会被清理。常见的清理方法有三种：

    1. 标记清理法：被标记的对象不会被清理，不被标记的对象会被清理。缺点是会造成内存碎片，因为对象无法拆分，必须放在一个连续的空间。
    2. 标记整理法：将没被标记的对象删除，将标记的对象全部前移。缺点是代价较大。
    3. 复制法：将标记的对象复制到一个新的内存区域。缺点是：占用两倍的内存空间。

    堆中包含新生代和老年代。

    1. 新生代结构：Eden + S0（From） + S1（To）。
2. Young GC流程：
   - Eden区满 → 触发Young GC → 存活对象移至To区 → To区变为新的From区。
   - 下次GC时（Eden区再次满时），From区和Eden区的存活对象移至新的To区，角色再次互换。
3. 对象晋升：
   - 年龄≥15次 → 晋升老年代。
   - To区空间不足 → 提前晋升。
4. Full GC触发：
   - 老年代满 → 触发Full GC（Old GC + Young GC）。
   - 采用标记-清除/整理算法，耗时较长。

    Note：

    当S0区或者S1区存放不了存活的对象时，会将存活的对象直接放入到老年代中。

    young GC、full GC会触发stop the world导致程序暂停。

    类加载器

    类加载器根据类的全限定名（如 com.example.MyClass）从类库中找到对应的字节码数据，加载到jvm虚拟机中。

    双亲委派机制：

    从Java虚拟机的角度来说，只存在两种不同的类加载器：一种是启动类加载器，这个类加载器使用C++语言实现，是虚拟机的一部分；另一种就是所有其他的类加载器，这些类加载器都有Java语言实现，独立于虚拟机外部，并且全部继承自java.lang.ClassLoader。

    从开发者的角度，类加载器可以细分为：

    • 启动类加载器：负责将 %Java_Home%/lib下面的类库加载到内存中（比如rt.jar）。
    • 扩展（Extension）类加载器：它负责将 %Java_Home%/lib/ext中的类库加载到内存中。
    • 应用程序（Application）类加载器：负责将系统类路径（CLASSPATH：运行程序所在目录）中指定的类库加载到内存中。

    除此之外，还有自定义的类加载器，它们之间的层次关系被称为类加载器的双亲委派模型。这种父子关系一般通过组合关系【通过parent引用指向父类，调用父类的loadClass方法，然后再执行自己的findClass方法】来实现。

    某个类加载器在接到加载类时，首先将加载任务委托给父类加载器，依次递归，如果父类加载器可以完成类加载任务，就成功返回；只有父类加载器无法完成此加载任务时，才自己去加载。

    使用双亲委派模型的好处在于具备了一种带有优先级的层次关系。例如类java.lang.Object，它存在在rt.jar中，无论如何加载，最终都是委派给处于模型最顶端的Bootstrap ClassLoader进行加载，因此Object类在程序的各种类加载器环境中都是同一个类。

    JVM调优

    默认设置下的JVM参数是很合理的，可以满足大多数的使用场景。但是，也有少量的场景需要对JVM参数进行优化。我们可以对CPU指标(通过命令行查看)、JVM内存指标(通过命令行查看)、JVM GC指标(通过GC日志查看)进行监控。

    举一个例子：服务频繁出现full GC(元空间或者老年代满时)，通过查看GC日志发现是元空间导致的full GC。通过观察元空间的使用参数。

    Metaspace       used 35337K, capacity 56242K, committed 56320K, reserved 1099776K
    • used ：已使用的空间大小
    • capacity：当前已经分配且未释放的空间容量大小
    • committed：当前已经分配的空间大小
    • reserved：预留的空间大小

    通过发现used和capacity差距较大，说明元空间存在内存碎片化的现象。这种现象多是因为每个classloader加载类时，元空间都会为它分配一个对应的chunk(元空间最小单位)，用来存储类的元数据以及方法区的字节码数据，只有当chunk满时，才会分配新的chunk。如果有过多的类加载器，就会出现内存碎片化的现象。

    dump输出堆的存储文件，查看堆的存储文件，发现有大量的delegateclassloader实例。原因为当一个方法的反射调用超过一定次数时，就会生成关于该调用的字节码数据，创建delegateclassloader去加载该字节码。当反射调用过多，就会导致创建大量的delegateclassloader，导致内存碎片化。

    可以通过调整元空间大小以及调整chunk大小、优化不合理的反射调用来解决该问题。

    springboot

    谈一谈对springboot的理解

    springboot就是基于spring的一个快速开发框架，底层就是spring。具有起步依赖【起步依赖其实就是各种starter，当你在pom.xml中引入starter时，会自动下载并导入与该场景相关的所有jar包（类库）】，还内嵌了tomcat；关键特色是springboot基于"约定由于配置"思想生成的产物，我们只要根据springboot的规则去编写对应的代码，就无需在进行大量的配置。

    springboot自动配置原理

    自动配置，就是自动实例化对象注入到IOC容器里面，在springboot应用里面，只需要在启动类上去加上@SpringBootApplication注解就可以去实现自动配置。@SpringBootApplication这个注解是复合注解，真正实现自动配置的注解是@EnableAutoConfiguration注解，自动配置的实现主要依靠三个核心的关键技术。

    • 引入Starter启动依赖组件的时候，组件里面必须要包含一个@Configuration配置类，而在这个配置类里面，我们需要通过注解@Bean去修饰需要添加到IOC容器里面的Bean对象。
    • 这个配置类是放在第三方的jar包里面，基于"约定优于配置"的理念，去把配置类的全路径放在classpath:/META-INF/spring.factories文件里面。SpringBoot就可以知道，第三方jar包里面这个配置类的位置，这个步骤主要是用到了Spring里面的SpringFactoriesLoader类来完成的。
    • Springboot拿到的配置类后，再通过Spring提供的ImportSelector接口，来实现对这些配置类的动态加载，将@Bean修饰的对象加载到ioc容器中。
    springboot启动流程
    1. 在springboot中，一般由SpringBootApplication注解修饰的类为主类，首先从main方法找到run()方法，在执行run()方法之前new一个SpringApplication对象。
    2. 调用run()方法，创建应用监听器SpringApplicationRunListeners开始监听。
    3. 然后加载SpringBoot配置环境(ConfigurableEnvironment)，然后把环境配置对象加入监听器对象中。
    4. 然后加载应用上下文(ConfigurableApplicationContext)，当做run方法的返回对象。
    5. 最后创建Spring容器，通过refreshContext(context)方法实现starter自动配置，包括spring.factories的加载以及ioc容器中bean的实例化。
    spring、springmvc以及springboot的区别
    1. spring：是一个ioc容器，用来管理bean，通过依赖注入来实现控制反转。提供了AOP机制，来实现公共行为和业务代码的分离，实现代码的复用；
    2. springmvc：是spring基于web的一种解决方案，定义了前置控制器DispatcherServlet来处理请求，通过HandlerMapping处理器映射器来找到对应的处理器，通过HandlerAdapter来执行处理器对应的方法，返回ModelandView对象给ViewResolver，对页面渲染，返回给用户；
    3. springboot：是基于spring的快速开发框架，内嵌了Tomcat服务器，可以通过起步依赖，来导入相关的jar包；更重要的是springboot是spring基于"约定大于配置"思想的产物，基于特定的规则编写代码，就可以避免进行大量的配置。

    在NIO模型中，Channel是用户空间对文件描述符（描述网络连接）的抽象封装，而轮询器负责监听、处理这些Channel的IO事件。其工作流程可概括为：

    1. 注册阶段： 将Channel对应的文件描述符注册到轮询器中；同时，用户空间通过系统调用将Channel对应的fd注册到内核的事件表中，同时声明关注的事件类型（如连接事件、读事件、写事件）。
    2. 轮询阶段： 轮询器通过系统调用进入内核空间，将监听的文件描述符交给内核，进入阻塞状态。此时内核会遍历所有轮询器监听的fd，并将就绪事件（如数据可读）通过共享内存返回给用户空间。
    3. 事件处理阶段： 轮询器根据返回的就绪事件，分配线程处理对应的IO操作（如读取数据）。

    相比传统模式，多路复用通过单次系统调用查询多个fd的状态，减少了用户态-内核态的切换次数。其中，select、poll、epoll是linux系统实现多路复用的几种方式，其中select和poll都是需要线性遍历所有fd，但是select方式的fd存储大小固定，poll使用动态数组存储，大小不固定；epoll使用红黑树管理fd集合，双向链表存储就绪事件，遍历时只会遍历双向链表中的就绪事件。

    PS：NIO相比于BIO可以实现更高的吞吐量。

    AIO（异步非阻塞式IO）：无需轮询器在进行轮询操作，内核空间主动通知用户空间有就绪事件。

    谈一谈你对Netty的理解
    1. Netty是一个基于NIO的高性能网络通信框架，是对NIO模型的一个封装，提供了很多的API，可以利用这些API去快速开发一个网络程序。
    2. Netty在NIO的基础上做了很多优化，比如：零拷贝机制以及高性能无锁队列，性能会比NIO更高。
    3. Netty支持多种网络通信协议，比如：Http、Websocket，针对拆包与粘包的问题，netty具有自带的编解码器来解决。
    4. 它也是很多框架的底层实现，比如RocketMQ、Zookeeper。
    Netty的核心组件以及作用

    主要由三层结构组成：网络通信层、事件调度层以及服务编排层。

    网络通信层包含了三个核心组件：Bootstrap、ServerBootStrap以及Channel，BootStrap负责客户端的启动，去连接远程的服务器；ServerBootStrap负责监听，会监听一个指定的端口号；Channel是一个负责网络通信的载体，每个Channel都会对应一个ChannelPipeline。

    事件调度层有两个核心的角色，EventLoopGroup【分为主从EventLoopGroup】以及EventLoop，EventLoopGroup本质上是一个线程池，负责监听IO事件，分配对应的线程去执行，EventLoop就相当于线程池中的线程，EventLoop【本质上由它执行handler】会将IO事件进一步分配给对应的ChannelPipeline进行处理。

    服务编排层有三个核心组件，ChannelPipeline、ChannelHandler以及ChannelHandlerContext，ChannelPipeline会将多个ChannelHandler组成一个链【输入对应一个链、输出对应一个链】，构成一个pipeline；ChannelHandler是对IO事件的处理器，相当于流水线上的员工；ChannelHandlerContext负责保存ChannelHandler的上下文信息，负责同一pipeline上不同ChannelHandler之间的交互。

    零拷贝

    传统的文件传输过程是通过read切换到内核态；通过DMA(直接内存访问)将数据拷贝到缓冲区；在将数据通过CPU拷贝到用户缓冲区，切换回用户态；通过wirte函数切换到socket缓冲区，通过CPU将数据拷贝到socket缓冲区；通过DMA(直接内存访问技术)拷贝将数据拷贝到网卡中；最后在切换回用户态。

    mmap可以减少一次CPU拷贝，直接将数据从缓冲区拷贝到socket缓冲区。

    sendfile可以减少两次切换。

    sendfile配合SG-DMA可以减少一次CPU的拷贝。

    reactor模式

    reactor模式代表一种高性能网络编程设计思想。reactor模式下包含两个核心组件，分别是reactor以及handler。

    1. reactor 主要负责 I/O 事件的监听【轮询器实现】以及分发【就是根据I/O事件类型创建对应的handler实例来处理】。
    2. handler主要用来处理具体的 I/O 事件。

    reactor模式主要包含单线程reactor模型以及多线程reactor模型。

    1. 单线程reactor模型表示所有的操作包括I/O事件的监听、I/O事件的分发以及I/O事件的处理都在一个线程中完成。当某个handler阻塞时，系统就无法处理其他的I/O事件。
    2. 多线程reactor模型主要分为一个reactor线程以及多个工作线程(存在于工作线程池)，reactor线程负责监听所有的I/O事件，根据事件类型创建对应的handler实例，其中reactor线程处理简单的业务逻辑，复杂的业务逻辑由reactor线程提交任务到工作线程池，由工作线程池中的工作线程处理。
    3. 主从多线程reactor模型分为主线程组、从线程组以及工作线程池。主线程组来监听和处理连接事件；从线程组用来用来监听和处理已连接socket的读写事件，复杂的业务逻辑会交给工作线程池进行处理。

    Mybatis

    Mybatis是什么？

    Mybatis是开源的持久层框架，封装了通过JDBC【一组java访问数据库的API】访问数据库的操作，无需开发在编写繁琐的JDBC原生代码。核心思想在于将程序中的SQL剥离出来保存在xml配置文件中，实现SQL与程序代码的分离，用户可以在xml配置文件中直接更改SQL语句，而无需对代码进行更改。

    补充：ORM对象映射模型，实现java中类对象和数据库中数据的映射。

    Mybatis和Mybatis-plus的区别
    1. Mybatis是开源的持久层框架，将SQL语句存储在xml配置文件中，实现了代码与SQL语句的分离。
    2. Mybatis-plus是在Mybatis基础上的增强工具，它可以简化分页查询以及动态SQL的实现，提供对应的API实现基础的增删改查操作，无需在编写基础的SQL代码。
    3. Mybatis-plus在Mybatis的基础上进行进一步的封装，简化了SQL的编写，适用于快速开发的场景。而Mybatis相较于Mybatis-plus可以实现高度定制化SQL语句的编写，适用于复杂场景。
    #{}和${}的区别

    使用#{}会被解析为预编译语句，使用？占位符替代#{}，数据库对预编译语句进行编译，编译好后，再将对应的值注入到编译好的SQL语句。

    使用${}相当于进行字符串拼接操作，直接将参数拼接到SQL语句中，然后交给数据库进行编译。

    {}可以避免sql注入的风险。

    SELECT * FROM user WHERE name = '; DROP TABLE user; --'  -- 无害字符串

    SELECT * FROM user WHERE name = ''; DROP TABLE user; --'
    一级缓存和二级缓存

    一级缓存是在sqlsession级别的缓存，一个sqlsession会话相当于一个事务，当在sqlsession中调用mapper方法查询时，会将对应结果进行缓存，如果在同一个sqlsession中再次调用相同的方法执行相同的操作，可以直接返回缓存中的数据，无需再从数据库获取数据。

    二级缓存是mapper层级别的缓存，多个sqlsession可以共享缓存。默认不开启，适用于读多写少的场景，因为每次进行数据的修改时，会将对应的缓存删除，会造成一定的开销。

    request.post()和session.post()的区别

    <font style="background-color:rgba(175, 184, 193, 0.2);">requests.post()</font> 和 <font style="background-color:rgba(175, 184, 193, 0.2);">session.post()</font> 的核心区别在于是否维持会话状态和连接复用。

    1. <font style="background-color:rgba(175, 184, 193, 0.2);">requests.post()</font> 每次发送请求都是独立的，不会自动保存 cookies，也无法维持会话状态，底层连接用完即释放；
    2. 而 <font style="background-color:rgba(175, 184, 193, 0.2);">session.post()</font> 会创建一个会话对象，自动保存服务器返回的 cookies（比如 sessionId），并且复用底层 TCP 连接。如果要做多个关联请求，推荐使用 <font style="background-color:rgba(175, 184, 193, 0.2);">Session</font>。
    3. 会话状态：用户登录后，服务器会创建一个 session，并通过 <font style="background-color:rgba(175, 184, 193, 0.2);">Set-Cookie</font> 返回一个 <font style="background-color:rgba(175, 184, 193, 0.2);">sessionId</font>，后续请求必须携带这个 <font style="background-color:rgba(175, 184, 193, 0.2);">sessionId</font>（通常在 Cookie 中），服务器才能获得对应的信息。

    xpath定位相比tagName、className、ID定位的好处

    tagName是根据标签名称进行定位，className是根据元素的class属性进行定位，ID是根据元素的id属性进行定位，而xpath既可以根据元素的属性进行定位、也可以根据文本内容进行定位，还可以根据元素的层级关系进行定位，还可以结合逻辑运算符进行定位。

    1. tagName，根据标签名定位
    2. className，根据标签的class属性定位
    3. ID，根据标签的id属性定位
    4. CSS selector，根据css选择器进行定位
    5. xpath，根据xpath进行定位

    xpath相比于css selector功能更加的强大，可以根据文本内容进行定位，也可以定位到父级元素，但是它的效率要低于css selector，因为它需要解析，还要遍历dom树来找到结果。

    什么是aop？**

    解释一下spring aop中的几个名词？**

    切面：指的就是切面类，管理着切点和通知。

    切点：指定哪些方法需要增强，哪些方法不需要增强，通过切点表达式实现。

    通知：将公共代码添加到业务逻辑中，通知包含多种类型可以添加到不同的位置。【前置通知、后置通知、环绕通知、返回通知、异常通知】

    连接点：被增强的业务方法。

    目标类：要增强的类。

    织入：就是将公共行为代码添加到需要增强的业务逻辑中去。

    通知有哪几种类型？**

    前置通知：目标方法执行之前调用。

    后置通知：目标方法执行之后调用，不关心方法是否能成功执行。

    返回通知：仅在目标方法成功执行并返回结果后被调用。

    异常通知：目标方法抛出异常后调用。

    环绕通知：前置通知 + 后置通知。

    实现原理：

    基于动态代理实现，动态代理主要分为JDK动态地理和cglib动态代理。

    • JDK 动态代理是基于接口进行代理，要求目标类必须实现特定的接口，JDK代理类会实现与目标类同样的接口；JDK 动态代理运行时生成的字节码数据是由JDK本身生成的；本质上是通过代理类的invoke()方法，利用java的反射机制去调用目标类的方法。
    import java.lang.reflect.InvocationHandler;
import java.lang.reflect.Method;
import java.lang.reflect.Proxy;

// 定义接口
interface Subject {
    void request();
}

// 实现接口的真实对象
class RealSubject implements Subject {
    @Override
    public void request() {
        System.out.println("RealSubject: Handling request.");
    }
}

// 实现 InvocationHandler 接口
class ProxyHandler implements InvocationHandler {
    private final Object target;

    public ProxyHandler(Object target) {
        this.target = target;
    }

    @Override
    public Object invoke(Object proxy, Method method, Object[] args) throws Throwable {
        System.out.println("Before method call");
        Object result = method.invoke(target, args);
        System.out.println("After method call");
        return result;
    }
}

// 测试代码
public class JdkDynamicProxyExample {
    public static void main(String[] args) {
        RealSubject realSubject = new RealSubject();
        ProxyHandler proxyHandler = new ProxyHandler(realSubject);

        Subject proxySubject = (Subject) Proxy.newProxyInstance(
                Subject.class.getClassLoader(),
                new Class<?>[]{Subject.class},
                proxyHandler
        );

        proxySubject.request();
    }
}

    操作系统相关知识：

    内核：

    逻辑上位于软件和硬件之间，可以理解为一个Lib库，提供了很多API供用户空间调用【系统调用】。用户空间程序通过系统调用来与内核交互，内核通过驱动程序来与硬件交互。【进程的调度、切换和内存管理都是在内核实现】

    用户空间和内核空间：

    用户空间主要包含用户应用程序、C库【来与系统调用交互，用户应用程序可以通过C库与系统调用间接交互，也可以直接与系统调用交互；通过C库调用，可以避免出现不同架构下指令不同的问题】。内核空间主要包含系统调用API、内核以及平台架构相关的代码(驱动程序)。用户空间 + 内核空间 + 硬件 = linux系统。

    进程和线程的区别**

    进程：一个正在运行的程序就可以理解为一个进程。进程是操作系统资源分配的最小单位，每个进程都有独立的内存空间（虚拟内存和MMU来实现的）。

    线程：一个进程可以包含多个线程。线程是CPU调度和执行的最小单位，属于同一个进程的线程可以共享内存空间。

    协程：是用户态（用户控制）的轻量级线程，协程的调度完全由用户决策，一个线程可以包含多个协程。

    协程的优势：

    协程的优势在于协程属于用户态的轻量级线程，协程的栈空间较小，占用内存较少。操作过程中，不会进行用户态和内核态之间的切换，不会产生对应的开销。

    虚拟内存机制和进程隔离如何实现？

    虚拟内存机制通过内存管理单元（MMU）和页表实现进程间的隔离。每个进程都拥有独立的虚拟地址，当访问内存时，CPU通过MMU将虚拟地址转换为物理地址，主要依赖于页表实现（页表号和页表内偏移）。页表中的权限位限制了他人内存的访问，从而确保了进程之间无法直接访问彼此的数据，实现了内存隔离。同时，虚拟内存采用按需分配策略，仅在进程实际使用时才分配物理内存，避免了资源浪费。

    用户态和内核态的区别？

    用户态和内核态是Linux系统中的两种运行状态。用户应用程序运行时一般处于用户态，权限较低，主要用于执行普通用户代码。当用户程序需要操作系统服务（如文件操作、内存管理）时，会通过系统调用切换到内核态。内核态具有高权限，可用于与硬件进行交互。交互完成后，内核态会切换回用户态，继续运行用户程序。

    进程之间的通信方式：

    管道：先进先出、单向流动、通信效率低。

    消息队列：有最大长度限制，保存在内核中，存在用户态和内核态之间的数据拷贝开销。

    信号：发信号通知进程执行相关操作。【事件通知】

    共享内存：映射到同一块内存。

    信号量：一种锁机制，配合共享内存一起使用。

    套接字：用于网络通信。

    CPU负载很高，但是利用率很低

    CPU的利用率是指实际执行任务的时间占总时间的百分比。

    CPU负载是指在特定时间内正在使用CPU（可运行状态）和等待资源（CPU和I/O）【不可中断睡眠状态】的进程数量。

    CPU利用率低，但负载高的最可能原因就是I/O瓶颈，磁盘I/O【进行很多的磁盘读写操作，很多进程在等待读写操作完成】以及网络I/O【等待网络响应，如：MYSQL产生死锁，一直得不到响应；NFS中的server挂掉，导致进程不断地请求却得不到响应】。

    如果想要查看这些数据，可以使用uptime查看CPU的负载情况，使用iostat -c查看CPU使用率，使用top查看不同进程的资源占用情况。

    物理层：用于节点之间的比特流传输。

    get请求和post请求的区别**

    （1）参数：

    get请求的参数一般放在URL里面，post请求的参数一般放在请求体里面。post请求的参数一般不能被浏览器保存，因为它的参数一般放在请求体里面，而不是放在URL里面。GET请求的参数虽然可以被浏览器缓存，但是也会受到URL长度限制；而且会暴露在浏览器历史中，安全性较差。

    （2）缓存行为：

    get请求可以被浏览器主动缓存，post请求想要被缓存需要进行手动设置。【因为post请求的参数放到请求体中，可能会改变服务器的状态】

    （3）编码支持：

    GET 参数必须进行 URL 编码。POST 可通过 <font style="background-color:rgba(175, 184, 193, 0.2);">Content-Type</font> 支持多种格式传输数据。

    （4）用法：

    GET请求一般用于获取数据，POST请求一般用于提交数据。

    TCP的三次握手**【一般在接收后，状态会发生变化】
    • 一开始客户端处于closed状态，服务端处于Listen状态
    • 第一次握手，客户端向服务端发送标志为SYN=1，系列号为seq=x的报文，发送完毕后进入SYN-SENT的状态，客户端接收到请求后变成SYN-RCVD的状态。
    • 第二次握手，服务端向客户端发送标志位为ACK=1、SYN=1，序列号为seq=y，确认号为ack=x+1的报文，客户端收到报文后变为ESTANBLISHED状态。
    • 第三次握手，客户端向服务端发送标志位为ACK=1，序列号为seq=x+1，确认号为ack=y+1的报文，服务端收到报文后变为ESTANBLISHED状态，建立连接。

    SYN可以理解为"想和你谈恋爱"、ACK理解为"好的"、seq立即为"我给你的钱数"、ack理解为"我想要的钱数"。

    为什么不是两次握手**
    • 如果因为网络问题，客户端一直没有收到服务端的响应，客户端就会发送多次请求，导致多次建立连接，浪费资源。【客户端只会发送一次ACK确认报文，保证服务器只会建立一次来连接，防止资源的浪费。】
    • 为了确保对方都具备收发能力。
    第一次握手的SYN报文丢失后，客户端的超时重传机制如何工作？

    假设初始超时时间为1秒，如果在1秒内没有收到服务器的SYN+ACK报文响应，会重新发送SYN报文。每次重传后，超时时间会翻倍来避免网络拥塞，一般重传的次数为5次。【对于linux操作系统：初始超时时间为1秒，重传次数为5次】

    Note：

    除了超时重传外，TCP还有快重传机制。

    TCP四次挥手【一般在发送后，状态会发生变化】**
    • 第一次挥手，客户端向服务端发送标志位为FIN=1、序列号为seq=u的报文，发送完毕后，客户端处于FIN-WAIT-1状态。
    • 第二次挥手，服务端向客户端发送标志位ACK=1、序列号seq=v，确认号为ack=u+1的报文，发送完毕后，服务端处于CLOSE-WAIT的状态，客户端收到后处于FIN-WAIT-2的状态。
    • 第三次挥手，服务端向客户端发送标志位FIN=1、ACK=1、序列号为seq=w、确认号为ack=u+1的报文，发送完毕后，服务端LAST-ACK的状态。【断开连接的报文】
    • 第四次挥手，客户端向服务端发送标志位为ACK=1，序列号为seq=u+1、确认号为ack=w+1的报文，发送完毕后，处于TIME-WAIT状态，服务端收到后处于CLOSED状态。等待2MSL后，客户端也变为CLOSED状态。【确认报文】

    客户端处于TIME-WAIT状态为什么要等待2MSL再变成CLOSED状态

    MSL是指最大报文生存时间。当服务端收不到客户端的确认报文时，会向客户端重新发送断开连接的报文。等待2MSL是为了避免客户端收不到服务端重传的断开连接的报文，而擅自断开连接，导致服务端无法释放连接（释放资源）。还可以保证与该连接相关的报文已经全部失效，不会对后续报文产生干扰。

    TCP和UDP的区别**
    • TCP是面向连接的，UDP是无连接的，TCP发送消息前必须建立连接，UDP发送消息前无需建立连接。
    • TCP传输效率较低，需要维护连接，要耗费一定的资源。UDP传输效率较高，常用来传输视频。
    • TCP能够提供可靠的交付【确认应答(接收方发送确认接收到的消息)和超时重传机制】，UDP不能提供可靠的交付。
    • TCP只支持一对一通信，UDP支持一对一、多对多等多种通信方式。

    输入一个不存在的IP地址，会发生什么？
    1. 当目标IP与客户端位于同一局域网时(网络号相同)，客户端会通过ARP广播查询目标IP对应的MAC地址。由于该IP地址不存在，客户端无法获取对应MAC地址，无法构造数据链路层帧，因此SYN报文根本无法发出，导致连接失败。
    2. 目标IP位于不同网络，客户端将SYN报文发送给路由器。路由器转发该报文，但由于目标IP地址不存在，客户端收不到确认报文，将触发TCP超时重传机制，经过多次重传仍未响应后，连接建立失败，最终由内核释放连接。
    对称加密和非对称加密的区别：

    对称加密协议：采用相同的密钥，加密解密速度快，缺点是安全性低，一旦密钥泄漏，数据就会被破解。

    非对称加密协议：采用不同的密钥，公钥和私钥。公钥是公开的，所有人都可以获得。私钥是私有的，由持有者持有，可以用公钥加密、私钥解密或者私钥加密、公钥解密。加密和解密的速度慢，但是安全性高。

    http1.0、http1.1、http2.0、http3.0的区别【当前用的最多的是1.1】
    • http1.0浏览器和服务器之间保持短连接【发送一次http请求响应后，就要断开TCP连接】；http1.0每次请求发送前都要等待上一个请求和响应完成，存在队头阻塞问题；http1.0不支持断点续传。
    • http1.1浏览器和服务器之间保持长连接；支持断点续传；无需等待上一个请求完成后，再发送当前请求，但是必须按照请求顺序进行处理和响应，如果一个请求处理的特别慢，后面的请求必须等待，所以也会存在一定的队头阻塞问题。
    • http2.0可以在一个连接中并发传输多个请求和响应，不用再像http1.1一样，按照顺序处理请求；http2.0采用二进制数据传输，不再采用文本数据传输，提高了传输效率；http2.0支持头部压缩，会删除多个请求相同的请求头部。
    • http3.0采用QUIC(快速UDP互联网协议)协议，使用UDP协议来替代TCP协议，传输多少数据就创建多少个stream流，当某个请求/响应丢失时，只会阻塞该流，并不会影响其他的流。
    什么是粘包和拆包
    • 粘包：多个数据包被合并成一个接收（如发送 A 和 B，接收为 AB）。【一个解决方案是将数据包固定长度，如100字节，不够的话使用字符进行填充，接收方每次接收100字节的数据】
    • 拆包：一个数据包被分割成多次接收（如发送 ABC，接收为 A 和 BC）。【也可以通过固定长度的方式解决】
    http协议和rpc协议的区别

    HTTP 是应用层协议，当前主流版本是 HTTP/1.1，不支持多路复用，默认文本格式传输（也可传二进制）。RPC 是远程过程调用机制，可基于 HTTP、TCP 等实现，传输效率更高。使用的gRPC 基于 HTTP/2，使用 Protobuf来序列化数据，使用二进制格式传输，支持多路复用（一个连接能够并发传输多个请求 / 响应），适合节点之间内部通信。

    补充：

    1. RPC的设计理念是向调用本地方法一样去调用远程的方法。
    2. RPC的服务发现，是通过引入中间服务，如：etcd以及redis，将服务名称、IP地址、端口号保存在数据库中，从数据库中获取服务对应的IP地址以及端口信息。
    3. RPC会建立一个连接池，来实现连接的复用。
    Cookie、Session、token的区别

    都是用来保存状态信息。

    • Cookie：当用户向服务器发送用户名密码等信息，服务器会进行校验，校验成功后，将相关信息存储在响应头的set-cookie属性中，传给客户端；客户端监测到set-cookie属性后，将相关信息存储到cookie中；下次传递在请求头中设置cookie属性，将它传输给服务端。缺点是：cookie存储在客户端容易被篡改。
    • Session：当用户当用户向服务器发送用户名密码等信息，服务器会进行校验，校验成功后，服务端会创建一个session来存储用户的相关信息；将sessionId存储在set-cookie属性中，传给客户端；客户端监测到set-cookie属性后，将相关信息存储到cookie中；下次传递在请求头中设置cookie属性，将它传输给服务端，通过sessionId找到session来获取相关信息。缺点是：不适用于集群环境。
    • token本质上就是一个加密字符串。可以使用JWT来生成，由JWT生成的token一般由三部分组成，头部(包含加密算法和token类型)、载荷(包含负载数据)【头部和载荷采用base64编码】以及签名【通过加密算法，利用密钥对头部和载荷通过加密生成的】。服务端将生成的token返回给客户端，客户端下次再请求头中设置token传输给服务端，服务端检验签名是否正确，正确就进行放行。
    滑动窗口机制（流量控制）
    • 为防止发送方发送太多的数据，接收方处理不过来，接收方会在确认报文中设置window字段，来告诉发送方滑动窗口的大小，来调整发送方的发送速率。其中，滑动窗口的大小是可以动态调整的，除了滑动窗口以外，发送速率还受到数据链路层的影响。
    • 发送方和接收方一样，也存在一个滑动窗口，它们的大小对应。主要分为已发送但未确认、可用窗口，滑动窗口前面是已发送并收到确认的，后面是不允许发送的。
    拥塞控制

    拥塞控制主要分为四个阶段：慢开始、拥塞避免、快重传和快恢复。

    • 慢开始：首先，将拥塞窗口的cwnd值（没收到确认前，能够发送的最大数据量）设置为MSS（最大报文大小），每经过一个往返时延，就将cwnd值加倍。
    • 拥塞避免：一旦cwnd值到达慢开始门限，执行拥塞避免算法，每经过一个往返时延，cwnd值 + 1。如果发送方认为网络出现拥塞（通过往返时延判断），就会将慢开始门限设置为之前的一半，将cwnd值设置为1，开始执行慢开始算法。
    • 快重传：一旦发送方连续收到三个重传确认【ACK报文】（比如：发送报文段1、2、3、4，连续发送三个确认号ack=2的重传确认，说明报文段丢失且网络状况良好），会立即重传对方未收到的报文段。
    • 快恢复：快重传后进入快恢复阶段，将慢开始门限设置为之前的一半，cwnd值等于慢开始门限，开始执行拥塞避免算法。

    实际发送的数据量大小是由滑动窗口机制和拥塞控制共同决定的。

    SSE和WebSocket的区别
    1. WebSocket是全双工通信协议，支持数据在客户端和服务端之间的双向流动。SSE是基于HTTP协议的一种轻量级解决方案，适用于服务端到客户端的单向数据流传输。
    2. WebSocket支持任意类型数据，SSE主要支持文本格式数据。
    3. SSE实现比较简单，相较于Websocket更加轻量，在单向数据流动的场景下更加高效。
    HTTP和WebSocket的区别

    http协议采用请求响应的模式，在HTTP1.0维持的是一个短连接。Websocket是一个全双工的通信协议，维持的是一个长连接。HTTP协议更适用于客户端单向请求的一个场景，而web socket适用于双向通信的一个场景。

    红黑树也是一种自平衡二叉搜索树，主要包含以下的特性：

    1. 所有节点要么是黑色、要么是红色。

    为什么使用B+树而不使用其它的树？

    B+树是一种多路平衡搜索树，根节点到每个叶子节点的路径长度相同；B+树的数据都存储在叶子节点，非叶子节点可以存储更多的索引键值，降低树的高度，减少磁盘的I/O次数，提高查询效率；叶子之间采用双向链表连接，范围查询更快。此外，B+树有自平衡特性，保证查询、删除和插入操作的时间复杂度为O(logn)。

    索引的底层原理

    B+树：相比于B（B-）树，B+树的优势在于它将数据全部存储到叶子节点，非叶子节点可以存储更多的索引键值，增加索引密度，降低树的高度，加快查询效率。同时，叶子节点之间使用双向链表连接，范围查询更快。B树将数据存储在所有节点。

    哈希索引：将列数据求出对应的哈希值，根据哈希值确定数据所在的行数，查询出对应的行数据。

    事务的ACID属性

    事务：一组SQL操作的集合。

    原子性：事务中的操作要么全部执行，要么全部回滚。

    一致性：事务执行前后，数据的状态必须一致。InnoDB 在事务提交时会检查所有约束（如外键、唯一性约束），确保数据的完整性和一致性。【转账时，总金额不变】

    隔离性：并发事务之间彼此互不干扰。

    持久性：事务提交后，数据将持久化存储。

    事务的四种隔离级别：

    读未提交：事务可以读取未提交的数据，可能会引起脏读（脏读：事务可能会发生回滚，导致读取到的数据和实际数据不一致）。

    读已提交【RC】：事务可以读取到已提交的数据，可能会引起不可重复读（不可重复读：多次读取到的数据不一致）。

    可重复读【RR】：默认级别，避免了脏读和不可重复读，但会导致幻读（幻读：多次读取到的结果集不同【锁不住间隙】）。

    串行化：直接使用表级锁。

    MVCC

    MVCC多版本并发控制，是一种无锁机制，可以实现事务之间的隔离。主要通过undolog日志的版本链、隐藏字段、readview实现。隐藏字段主要包含操作数据的事务ID以及指向前一个版本的回滚指针。readview主要包含四个字段：当前活跃的事务ID列表，活跃的最小事务ID、活跃的最大事务ID+1以及创建readview的事务ID，如果操作数据的ID小于活跃的最小事务ID，就可见；大于等于活跃的最大事务ID+1就不可见；当活跃的事务ID列表中，如果操作数据的ID为当前创建readview的ID就可见，否则就不可见。在读已提交隔离级别下，每次访问都会创建一个readview，在RR隔离级别下，每次事务执行会创建一个readview，可以在一定程度上解决可重复读隔离级别下的幻读问题。

    锁的类别：

    按照粒度划分：行锁、表锁、页锁。

    按照类别划分：可以分为共享锁和排他锁。

    乐观锁与悲观锁：
乐观锁认为冲突不会频繁发生，只在数据提交时通过时间戳或者版本号来判断是否发生冲突，冲突就回滚事务【或者使用数据的目标值(原始值)和当前值进行比较】。
悲观锁认为冲突会频繁发生，所以在对数据操作时，会直接上锁，不让其它事务去操作该数据。

乐观锁的使用场景：读多写少，并发冲突概率低的场景。
悲观锁的使用场景：写多读少，并发冲突概率高的场景。

共享锁与排他锁：
排他锁：又称为写锁，但对数据进行增删改操作时，数据库会默认加上排他锁，排他锁和共享锁是悲观锁的一种实现形式，在事务对数据进行写操作时，不允许其它事务对该数据进行读取和修改。
共享锁：又称为读锁，在事务读取数据时可以加上共享锁，允许其它数据对该数据进行读取操作，但不允许其他事务修改该数据。

    其它的锁：意向锁、间隙锁和临建锁。

    意向锁（innodb特有）：意向锁是一种表级锁，可用来快速判断能否在表上加入对应的锁。当在某一行加上共享锁时，数据库会在表上加上意向共享锁。当在某一行加上排他锁时，数据库会在表上加入意向排他锁。

    间隙锁：
属于innodb搜索引擎，只在可重复读隔离模式下有效。可以锁住索引记录之间的"间隙"，防止幻读。

    什么是死锁？

    两个事务互相等待对方释放锁（资源），而陷入冲突。例子：事务1，具有id=1数据的锁；事务2，具有id=2数据的锁；事务1想要获取id=2的锁，事务2想要获取id=1的锁，导致陷入冲突。【事务只有全部处理完毕后才可以释放锁】

    如何避免：

    1. 采用固.定的加锁顺序。
    2. 避免大范围加锁。
    3. 减少事务的执行时间。
    死锁的四个必要条件【互等不还】
    1. 互斥：某种资源一次只允许一个事务访问。
    2. 占有且等待：一个事务已经占有一些资源，在等待其它资源的释放。
    3. 不可抢占：某种资源在事务使用完毕前，不允许被抢占。
    4. 循环等待：存在一个事务链，每个事务都占有其它事务所需的至少一种资源。
    聚簇索引（一级索引）和非聚簇索引（二级索引）

    聚簇索引和非聚簇索引的主要区别就是叶子节点是否存储整行的数据。在innodb数据库引擎中，主键索引为聚簇索引，非主键索引为非聚簇索引，聚簇索引根据主键值构建B+树，叶子节点存储整行的数据（主键值与行数据对应）。非聚簇索引的叶子节点存储索引列的值以及对应的主键值。有时候会发生回表现象，就是根据索引列的值查询到对应的主键值，在根据主键值从聚簇索引中查询到对应的行数据。在MyISAM数据库引擎中，主键索引和非主键索引一般都是采用非聚簇索引，叶子节点存放列值以及对应数据的存放位置，根据存放位置找到对应的数据。

    回表现象：就是需要根据当前列值获取主键值，再根据主键值从主键索引中获取数据。

    索引失效

    模型数空运最快

    模糊查询：使用LIKE进行模糊查询，以%开头会导致索引失效。如果是a%可能不会导致索引失效，因为比如数据库中存储abc、abd、bcd，数据库可以根据a%找到以a为开头的字符串，通过双向链表找到对应的值，当然如果以a开头的单词过多，会导致索引失效【使用B+树存储】。

    型：数据类型不一致会导致索引失效，比如索引列是CHAR类型，你查询的是int类型。

    数：对索引列使用内部函数会导致索引失效，比如length()，因为索引树不是根据函数生成。

    空：使用is NOT NULL或者<>进行判断时，可能会导致索引失效。

    运：对索引列进行四则运算，可能导致索引失效，索引列的值和索引树的值不对应。

    最：要满足最左前缀匹配原则，比如使用a、b、c建立索引，不能写成a=0、c>5的形式。

    快：当全表查询更快时，可能不会走索引。

    索引下推

    如果有一个表students，有一个组合索引(name, age)，你需要进行条件查询select * from students name="Li" and age>20。

    非索引下推：根据name字段从二级索引中查询到主键的ID，根据主键ID回表查找到对应的行数据，在使用行数据判断age是否大于20。

    索引下推：就是根据name字段先从二级索引中找到对应的记录，提前使用age字段对记录进行过滤，然后再根据记录对应的主键进行回表，找到完整的数据，可以减少回表的次数。

    分库分表

    分为水平分表、垂直分表、水平分库以及垂直分库。

    • 水平分表：数据量太大，按照行方向将数据分成多张表；一般可以采用哈希取模（求哈希值后取模）以及范围划分（根据时间戳拆分，实现冷热数据分离）【水平分库类似】---> 数据量太大，会导致查询速度变慢。
    • 垂直分表：数据量太大，按照常用字段和不常用字段分成多张表。（实现冷热字段分离） ---> 数据量减少；降低锁的开销，列数太多加锁慢；减少I/O操作次数，数据库按照数据页存储，数据页的大小固定，列数多存储的行数变少。
    • 垂直分库：按照业务将一个数据库拆分成多个数据库，存储在不同服务器中。【可以避免某一数据库瘫痪，导致整个程序失效】
    主从复制原理

    主从复制可以用于故障切换、读写分离、数据备份。

    当主库执行写操作时，变更会被记录到二进制日志（Binlog）中。主库的 Binlog Dump线程 主动将新产生的 Binlog 事件发送给从库。从库的 I/O线程 接收这些事件，并写入本地的 中继日志（Relay Log）。随后，从库的 SQL线程 会实时监控中继日志，一旦发现新事件，立即解析并在从库执行对应的 SQL 操作，从而实现主从数据的同步。【三线程两日志】

    复制模式：

    异步模式

    主库执行写操作后，将变更记录到 Binlog日志 并直接返回客户端，无需等待从库确认。

    半同步模式

    主库执行写操作后，需等待至少一个从库确认已接收 Binlog事件 并将其写入本地中继日志（Relay Log），才会向客户端返回结果。

    全同步模式

    主库执行写操作后，需等待所有从库均确认已接收 Binlog事件 并写入中继日志，才会向客户端返回结果。

    缓存击穿、缓存穿透以及缓存雪崩

    缓存击穿：redis中的一个热点key在不停地扛着高并发，当这个key失效的瞬间，大量请求穿透缓存请求数据库，并将数据设置到redis中，导致性能下降。

    解决方案：设置永不过期、加锁排队【在查询缓存中是否存在，不存在就从数据库中查询，并保存到缓存中的逻辑代码部分加入锁机制，使用双重检查锁】

    @SuppressWarnings("unchecked")
public List<ProductCategory> findProductCategory() {
    String key = "product:product-category";
    // 一重锁
    Object obj = redisTemplate.opsForValue().get(key);
    if (obj == null) {
        synchronized (this) {
            // 二重锁
            obj = redisTemplate.opsForValue().get(key);
            if (obj != null) {
                return (List<ProductCategory>) obj;
            }
            List<ProductCategory> categoryList = productCategoryMapper.selectProductCategory();
            redisTemplate.opsForValue().set(key, categoryList, Duration.ofHours(2));
        }
    }
    return categoryList;
}

    缓存雪崩：缓存集中过期，或者缓存服务器宕机，导致大量请求直接访问数据库，导致数据库压力过大，宕机。

    解决方案：加锁排队 + 随机失效时间、部署缓存服务器集群。

    缓存穿透：就是缓存中请求数据不存在，数据库中请求数据也不存在。很有可能是攻击者进行恶意攻击。

    解决方案：参数校验、缓存空对象。

    redis持久化

    概念：将存储在内存中的数据备份到磁盘中，一般有两种实现方式，RDB持久化以及AOF持久化。

    RDB持久化：每个一段时间将内存中的数据，备份到磁盘中。使用RDB格式的文件存储，采用二进制压缩存储的方式，不断地更新RDB文件。好处在于数据恢复速度较快，坏处在于数据安全性较低。

    AOF持久化：将对于服务器所有的写操作保存在AOF格式的文件中，在服务器恢复的时候，重新执行命令来恢复数据，好处在于数据安全性较高，坏处在于当AOF文件过大时，可能会对redis性能产生影响。

    redis线程模型

    redis是单线程的，内部使用文件事件处理器，主要由四部分组成多个socket、IO多路复用程序、文件事件分派器以及事件处理器。具体结构如下：

    多个socket包含一个负责监听的socket，以及多个与客户端建立连接的socket。当客户端发来请求时，IO多路复用程序会将产生的事件(AE_READABLE事件以及AE_WRITABLE事件放入到事件队列中)，由文件事件分派器交给不同的事件处理器进行处理。AE_READABLE事件主要包含建立连接的请求以及处理数据的请求，如果是建立连接的请求就会交给连接应答处理器进行处理；如果是处理数据的请求就会交给命令请求处理器进行处理；处理完毕后，产生AE_WRITABLE事件放入到事件队列中，交给命令回复处理器进行处理。

    redis过期策略和内存淘汰机制

    过期策略主要分为定期删除策略以及惰性删除策略。

    定期删除策略：redis的存储结构其实相当于一个字典，键为字符串类型，值为redis中的各种类型，redis中的数据存储在这个字典中。定期删除策略是指每过一段时间就从字典中随机选取20个键，删除其中过期的键，如果过期的键的数量超过1/4，就会再次重复上述步骤。

    惰性删除策略：就是在客户端访问这个key时，检查这个key是否过期，如果过期了就删除这个key。

    内存淘汰机制：redis会设置一个最大使用内存maxmemory，如果超过了maxmeory最大使用内存，就会执行淘汰算法，常见的淘汰算法如下：

    1. 默认策略：不淘汰，只是不让往里写。
    2. volatile-lru：只淘汰设置了过期时间的key，删除最久未访问的key。
    3. volatile-ttl：也是只淘汰设置了过期时间的key，ttl【剩余生存时间】越小越先淘汰。
    4. volatile-random：随机淘汰一个key。
    5. allkeys-lru：淘汰的对象是全体key的集合，也是删除最久未访问。
    6. allkeys-random：随机淘汰一个key。
    redis集群——主从模式、哨兵模式以及高可用集群模式【分片集群】

    主从模式：

    分为一个主节点，以及多个从节点。其中，主节点用来对外提供服务，从节点是主节点的一个备份节点，从节点的数据会从主节点同步过来，主要起到数据备份的作用。主节点宕机，需要运维人员、运维脚本来选取新的从节点作为主节点。

    哨兵模式：

    哨兵模式会·借助哨兵sentinel来监控master节点的状态，客户端通过哨兵集群来获取master的网络地址信息，对master进行访问。当master节点异常时，会通过raft算法选取一个新的slave节点来替代主节点的角色。但是，哨兵模式存在访问瞬断【主从切换时，对集群的访问会短暂失效】的问题；同时，哨兵模式只有一个主节点对外提供服务，一般一个redis占用内存大小最好为10G，否则会影响主从同步效率以及数据恢复。

    高可用集群模式【分片集群】：

    该模式是由一个或者多个主从节点群组成的分布式服务器集群，所有的数据会平分给所有的主节点。相比于哨兵模式，对系统的影响会小很多，比如：访问瞬断，对主从同步效率以及数据恢复的影响。

    常见的限流算法

    固定窗口算法

    将单位时间段（比如：1s）当作一个窗口，使用计数器来记录窗口接收的请求次数，如果超过限流阈值，就拒绝接收后续请求。

    缺点：如果限流阈值为5，单位时间段为1s，在0.8s-1s之间发送5个请求，在1s-1.2s之间发送5个请求，并不会受到限流的限制，但是在0.8s-1.2s之间接收的请求次数为10，已经超过了单位时间段内不能超过5个请求的限制。

    滑动窗口算法

    将单位时间周期划分为n个小周期，如：单位时间为1s，划分为5个小周期（每个小周期为0.2s），每个小周期都有独立的程序计数器，每经过0.2秒，时间窗口就向右滑动一格，抛弃过期的小周期。它就可以很好地解决上述的临界问题，在0.8s-1s内会发送5个请求，此时时间窗口的范围是0-1s，此时滑动窗口的请求数等于限流阈值，不会接收请求。再过0.2秒，时间窗口向右移动一格，时间窗口的范围是0.2s-1.2s，由于窗口的请求数等于限流阈值，所以不会再接收1s-1.2秒间发送的5个请求。

    缺点：一旦达到限流阈值，后续的请求会被直接暴力拒绝，导致损失一部分请求。

    漏桶算法

    漏桶算法面对限流更加的柔性，可以看成注水和漏水的过程。以任意速率注水，以固定速率出水，一旦水超过桶的容量，就会拒绝请求。注水相当于对于系统的请求，速率不固定；桶容量，代表系统所能处理的并发请求数；漏水，代表系统以固定的速率处理请求。

    缺点：没有办法很好地应对突发流量。

    令牌桶算法

    根据限流的大小往令牌桶里面放入令牌，一旦超过令牌桶的容量，就会被丢弃。在处理请求时，系统会先向令牌桶中去拿令牌，然后在执行处理逻辑。拿不到令牌，就拒绝执行此请求。令牌桶算法可以根据流量的变化，来调整令牌的发放速率，能够更好地应对突发请求。

    Raft共识算法【选举部分】

    在Raft算法中，每个节点都会处于以下这三个状态之一：candidate(候选人)、follower(跟随者)以及leader(领导者)。每个节点之间通过RPC协议进行通信。

    Raft算法中还包含一个任期的概念，相当于一个计数器。

    选举过程：

    每个节点等待领导者节点心跳信息的超时时间都是随机的。比如A节点等待超时的时间间隔为150ms，B节点200ms，C节点300ms。超时后，会从follower状态切换为candidate状态并发起投票，将自己的任期值+1，并给自己投一票，向其他节点发送请求投票的RPC消息【每个节点在一个任期内（自己当前任期）只能投一票，根据任期号和日志编号进行投票】。当节点收到大多数节点的投票(n/2 + 1)，就会成为新的领导者。

    投票规则：

    • 若候选者任期号 小于 自身任期：直接拒绝投票。
    • 若候选者任期号 等于 自身任期：仅当自身尚未在该任期投票，才会进入日志判断环节【日志主要由任期号和日志索引组成，一般先比较任期号，在比较日志索引】。
    • 若候选者任期号 大于 自身任期：先将自身任期更新为候选者的任期，再进入日志判断环节。

    领导者会在固定的时间间隔给其它节点发送心跳消息【candidate收到新leader的心跳后，如果新leader的任期号不小于自己当前的任期号，那么就从candidate回到follower状态；如果领导者节点发送消息的任期号大于跟随者节点的任期号，跟随者节点会立刻更新任期号】。如果领导者发现自己的任期编号比其他节点小，就会立即切换回跟随者的状态。

    防止脑裂的问题【多个节点当选领导者】：

    通过设置随机的心跳信息超时时间以及随机的选举超时时间【这两个时间不是一致的】，来保证大多数情况下，只有一个节点发起选举，而不是同时发起选举，来防止票数的瓜分。

    如何保证日志同步？

    1. 主要是通过多数派提交机制和日志对齐机制来实现的；
    2. 多数派提交机制是指在客户端进行操作时，会将操作作为日志条目，添加到自己的日志中，同时会将日志条目复制到其它跟随者节点中，只有半数以上跟随者节点更新完成日志后，才提交该"条目"；
    3. 日志对齐机制是指当出现日志不对应的情况时，找到领导者节点和跟随者节点对应上的最后一个日志，来更新覆盖后面的日志。

    边缘自治项目

    领导者选举机制
    1. 每个节点都有不同的接收领导者节点心跳信息的超时时间，当超过超时时间，会将自己从follower状态切换到candidate状态，然后发起选举。
    2. 广播自己的任期号以及当前负载状况，如果发起选举的节点的任期号大于等于当前节点，且发起选举节点的负载状况优于当前节点【根据LRP算法进行衡量】，就会获得一张选票【每个节点在一个任期内只能投一票】，当获取超过半数的选票，就会成为领导者，切换到leader状态，来管理集群。此外，发起选举的节点也会存在选举超时时间，如果选举超时，会增加任期号，重新发布选举过程。LRP算法公式如下：

    1. 领导者节点会定期向跟随者节点发送心跳检测消息，如果遇到任期号大于自己的节点会切换到follower状态。

    Note：选举超时时间（1000ms）一般要远大于心跳超时时间（150ms），因为心跳超时主要是领导者节点和从节点之间的单向通信，然后选举超时需要经过多个节点之间的双向通信。

    Note：设置任期号可以避免出现双主的一个状况。因为一旦领导者节点失联，我们会从集群中选举出一个新的领导者节点。为了避免失联后的节点重新加入集群而造成有两个主节点的现象，所以设置了任期号，根据任期号可以使已经过期的主节点可以切换到跟随者状态，确保集群中只有一个领导者节点。

    心跳机制

    当客户端与服务端建立连接时，会在redis中存储一个心跳【当用户在其它地方登录时，可以判断用户是否已经登录】，服务端每次收到客户端发送的心跳检测消息，就会更新一次，60秒内没收到消息，服务端就把对应的通道断开，删除token以及心跳缓存。主要通过IdleStateHandler【状态处理器】以及实现ChannelDuplexHandler【双向处理器】的HeartBeatHandler类实现，如果60秒内没有读操作发生，IdleStateHandler就会触发READER_IDLE事件并向下传递，HeartBeatHandler类的userEventTriggered方法会捕获到READER_IDLE事件，通过ChannelHandlerContext获取对应的Channel将它关闭。

    消息发布订阅机制

    包含两个核心函数，一个是订阅函数，另一个是发布的函数。主要通过RTopic类实现，订阅函数使用@PostConstruct修饰【当前bean初始化完成后调用】，根据"主题"获取RTopic对象，通过addListener方法设置监听的消息类型【消息类】。发布函数根据"主题"获取RTopic对象，调用publish方法来发布消息。每个服务器都订阅了该主题，因此都会接收到对应的消息，通过哈希表根据消息中的receivedId找到对应的Channel，如果Channel存在就发送消息。

    离线消息补发机制

    用户的消息包括发给用户的消息以及发给用户所在群组的消息，首先获取用户的退出时间last_off_time，查找发给用户或者用户所在群组的消息，判断消息发送时间send_time是否大于用户的退出时间，如果大于代表是离线消息，将离线消息通过sendMsg方法一次性发送给用户。

    加好友操作

    主要分为两个阶段：好友申请阶段、处理申请阶段。

    （1）好友申请阶段：传入参数——联系人id和申请信息。首先判断联系人表中是否已经包含对应数据，且处于"被拉黑"状态，如果处于则提示用户“对方已经拉黑，无法添加”；如果处于FRIEND状态，就提示“已经是好友，无需在申请”。获取联系人信息，判断联系人类型，如果为群组，则获取群主id（因为申请消息是发送给群主的）；同时，获取该联系人的添加类型，如果类型为直接添加，则直接添加为好友【进行一系列操作，即：如果联系人为群组，则判断群组是否已经达到最大人数，达到就通知申请失败；添加好友时，如果联系人为用户，那么会在联系人表中创建”两条数据“，否则就创建一条数据；同时更新缓存中用户的联系人列表；然后，创建会话，在会话信息表、会话用户表【一条或者两条数据】、聊天信息表中插入数据【申请消息，注意：消息一般不会同时插入两条】，如果联系人是用户，则调用两次sendMessage方法【消息内容一样，消息类型不一样，用以区分】，分别发送消息给申请人和联系人；否则，会将用户的通道加入到群组通道中，同时向群组发送消息（其实是向ChannelGroup中的每个Channel发送消息）】。如果添加类型为需要审核，就添加申请信息到申请信息表，同时发送申请消息给"接收人"。

    （2）处理申请阶段：传入applyid以及处理状态status，更新用户申请表中对应数据的"状态"字段，如果同意加为好友，就进行上述的一系列操作。如果是拉黑用户，会判断联系人表中是否存在主键为（申请用户id，联系人id）的数据，如果存在就更新状态，否则就插入两条数据到（拉黑，被拉黑）。

    文件秒传的时候发生MD5冲突怎么办？比如用户上传的是A文件，但是他与我们服务器中B文件的MD5值是一样的（哈希冲突），那么在这种场景下用户上传A，执行秒传逻辑后实际上存储的是B，我们如何优化这种哈希冲突？

    视频处理方法

    提出了一种基于滑动窗口的边缘动作识别框架，主要分为五个模块：

    1. 视频流收集模块：利用缓存数据库【redis存储二进制格式的数据】来处理输入速度和模型推理速度不一致的问题；【threading模块实现双线程】
    2. 视频预处理模块：通过预处理技术，来保证帧格式的一致性；
    3. 动作识别模块：识别为动作、模糊窗口或者背景窗口；每次处理16帧，应用在视频中大概17-18fps【没使用滑动机制，大概在5-6fps】，准确率为62%【使用后的准确率为60%】；
    4. 滑动窗口模块：计算帧之间的相似度，来控制滑动窗口进行滑动；
    5. 用户界面

    滑动机制：

    主要靠动作识别模块与滑动窗口模块相互配合完成。动作识别模块逐帧检测，每次输入16帧的视频进行检测；滑动窗口模块通过计算相似度来实现滑动，对于背景和模糊类型有不同的计算方式。

    背景图像的相似度计算：

    对于背景图像重要的是判断是否存在新的动作，所以需要将前景和背景分离，根据相似度变化来判断是否存在新的动作。

    具体实现方式为：利用GMM高斯混合模型来区分前景和背景，使用皮尔逊系数来计算两个帧之间的相似度，超过阈值就判定为背景，否则为非背景。

    GMM高斯混合模型：对于图片来说，背景的像素值是相对稳定的，当动作出现时，像素值会突然性地发生变化。GMM就是根据一段时间的像素值来建立高斯分布曲线，并根据当前像素值对应的高斯分布来判断它属于经常出现的模式还是不经常出现的模式，以此来判断是前景还是背景。α用来衡量不同高斯分布出现的概率。如果高斯分布曲线不包含该高斯分布，就使用当前的高斯分布曲线来替代α最低的高斯分布。

    模糊图像的相似度计算：

    模糊图像包含动作发生的前兆，既不属于动作窗口，也不属于背景窗口。使用帧间差分法来比较两个帧之间的相似度，为了避免两个帧之间相似度太高而出现的漏检问题。不但比较当前帧与上一帧的相似度，还比较当前帧与第一个模糊帧的相似度，从局部差分和全局差分的角度来防止漏检问题。【在模糊情况下，很难区分前景和背景，要保证不丢失动作趋势】

    与Yolo的区别：

    Yolo主要是用来判断图像中是否存在对应的目标，而不是识别目标的行为。边缘动作识别是识别目标的行为，对目标的行为进行理解。

    丢帧的问题如何解决：

    就是可以有两种解决方案，首先摄像头会为每帧设置一个帧号，根据帧号可以判断是否丢帧。解决方案一种是根据全局差分以及局部差分，如果上一帧丢失，可以根据累计的变化来判断是否出现有效的动作。另一种就是直接送入模型识别。

    黑盒测试、白盒测试、灰盒测试相关总结：

    什么是缺陷？

    • 所有不满足需求和超出需求的都是缺陷。
    • 没有不存在缺陷的软件，只有尚未发现的缺陷。

    什么是黑盒测试？**

    • 就是将测试对象看成一个黑盒子，完全不管它的内部实现，只通过软件的外部表现来发现缺陷。

    黑盒测试用例设计方法主要分为：**

    • 等价类划分、边界值分析、因果图法、正交实验设计、功能图分析、错误推测、需求文档转化。

    等价类划分：**

    • 定义：将输入域(输入的一个范围)划分为若干部分，每一部分的代表性数据在测试中的作用等价于这一类中的其他值。
    • 等价类划分：有效等价类、无效等价类。有效等价类例子：长度在6到18个字符之间、可以包含字母、数字和下划线、以字母开头、不为空、不重复、不含空格且区分大小写的字符串。而无效等价类则包括：长度小于6或大于18、包含非字符、非字母、数字和下划线的字符、不以字母开头、为空、重复、包含空格且不区分大小写的字符串。

    边界值分析：**

    • 对输入或输出的边界值进行测试，通常作为等价类划分法的补充。
    • 主要分为上点【边界上的点】、离点【边界上的点】和内点【输入域内的点】。举个例子：如果输入域为(6, 18)，那么上点为(7, 17)，离点为(6, 18)，内点为(8, 16)。

    什么是白盒测试？

    • 把测试对象看成一个透明的盒子，通过对程序内部结构分析、检测来寻找问题。下面的几种白盒测试方法了解一下即可：
    语句覆盖（Statement Coverage）：
    • 目标是确保程序中的每一条语句至少被执行一次。

    分支覆盖（Branch Coverage）：

    • 目标是确保程序中的每个分支（即if-else语句中的每个可能路径）至少被执行一次。

    路径覆盖（Path Coverage）：

    • 目标是执行足够的测试用例，以确保程序中的每一条可能的执行路径都被覆盖。

    条件覆盖（Condition Coverage）：

    • 目标是确保每个布尔子表达式（即if语句中的条件）的每个可能结果（真或假）至少被执行一次。

    判定/条件覆盖（Decision/Condition Coverage）：

    • 结合了分支覆盖和条件覆盖，确保每个判定的每个可能结果至少被执行一次。

    条件组合覆盖（Condition Combination Coverage）：

    • 目标是测试所有可能的条件组合，确保每个条件的所有可能组合都被执行。

    路径条件覆盖（Path Condition Coverage）：

    • 结合了路径覆盖和条件覆盖，确保每条路径上的所有条件都被测试。

    循环覆盖（Loop Coverage）：

    • 目标是测试循环的不同迭代次数，包括零次、一次、多次以及循环边界值。

    数据流覆盖（Data Flow Coverage）：

    • 关注程序中数据的流动，确保所有可能的数据流路径都被测试。

    变异测试（Mutation Testing）：

    • 通过引入小的、有意的代码更改（变异），然后检查测试用例是否能检测到这些更改，以此来评估测试用例的有效性。

    什么是灰盒测试？

    灰盒测试是介于白盒测试和黑盒测试之间的一种测试方法，多用于集成测试阶段。目前互联网上使用最广泛的就是灰盒测试。

    黑盒测试与白盒测试的优缺点？

    黑盒测试

    （1）优点：

    1. 比较简单，不需要了解程序的内部实现。
    2. 从用户的角度出发，容易发现业务中存在的问题。

    （2）缺点：

    1. 只是根据输入和输出进行判断，可能忽视系统中存在的比较严重的bug。

    白盒测试

    （1）优点：

    1. 能够发现代码中所隐藏的问题。

    （2）缺点：

    1. 测试人员基于代码进行判断，可能遗漏一些功能需求。
    2. 系统庞大时，测试开销会非常大。

    如何使用jmeter进行压力测试？
    1. 创建测试计划：
      • 打开JMeter，选择“文件”->“新建”，创建一个新的测试计划。
      • 在测试计划中添加一个线程组（Threads Group）。
    2. 配置线程组：
      • 线程数（Number of Threads）：设置你想要模拟的并发用户数。
      • 准备时间（Ramp-Up Period）：设定JMeter完成启动所有线程所需的时间。例如，如果你设置了100个线程和10秒的准备时间，JMeter将尝试每秒启动10个线程。
      • 循环次数（Loop Count）：设置每个线程执行测试的次数。如果你想让每个用户只执行一次，请设置为1；如果需要多次执行，则相应增加这个数值。
    3. 添加取样器（Sampler）：
      • 右键点击线程组，选择“添加”->“取样器”->“HTTP请求”或其他类型的请求（根据你的测试需求）。在这里，你需要指定请求的方式（GET、POST等）、URL以及其他必要的信息。如果需要还需右键点击http请求，添加请求头。
    4. 添加监听器查看结果【可以作用于单个请求，也可以作用于同一线程组的所有请求】：
      • 为了分析测试结果，你可以添加监听器如“查看结果树”、“聚合报告”。这些监听器可以实时显示测试过程中的响应时间、吞吐量、错误率等关键指标。
    5. 添加配置元件
      • 添加配置元件，如："CSV数据文件设置"，来设置参数，将参数与CSV中的数据绑定。【PS：对于excel文件，可以转换成csv文件进行处理；csv data set config也可以读取txt文件，但是txt文件要满足特定的规则】
    如何使用jmeter进行接口测试？
    1. 创建测试计划：
      • 打开JMeter，选择“文件”->“新建”，创建一个新的测试计划。
      • 在测试计划中添加一个线程组（Threads Group）。
    2. 配置线程组：
      • 线程数（Number of Threads）：设置你想要模拟的并发用户数。
      • 准备时间（Ramp-Up Period）：设定JMeter完成启动所有线程所需的时间。例如，如果你设置了100个线程和10秒的准备时间，JMeter将尝试每秒启动10个线程。
      • 循环次数（Loop Count）：设置每个线程执行测试的次数。如果你想让每个用户只执行一次，请设置为1；如果需要多次执行，则相应增加这个数值。
    3. 添加取样器（Sampler）：
      • 右键点击线程组，选择“添加”->“取样器”->“HTTP请求”或其他类型的请求（根据你的测试需求）。在这里，你需要指定请求的方式（GET、POST等）、URL以及其他必要的信息。如果需要还需右键点击http请求，添加请求头。
    4. 添加断言：
      • 右键http请求添加断言，主要分为响应断言以及json断言，响应断言默认会根据状态码进行断言，当状态码>=400时就会报错，json断言会通过json提取器获取数据，根据数据内容进行判断。
    5. 添加监听器
      • 右键http请求，添加结果树，来查看请求是否成功。
    如何通过jmeter判断程序已经达到性能瓶颈？

    可以通过错误率、吞吐量、响应时间等指标来进行判断。如果错误率大于1%说明系统达到瓶颈；如果响应时间稳步上升，并且在可接受范围内，说明系统正常运行，如果响应时间急剧上升（300ms -> 3s），说明系统出现瓶颈；如果吞吐量随着用户数线性增长，说明系统扩展性好，如果吞吐量增长缓慢甚至下降，说明系统达到瓶颈。

    禅道中bug的状态及生命周期：
    1. 激活
    2. 已解决
    3. 已关闭

    生命周期：

    （1）测试人员提交缺陷，状态为激活，未确认，分配给测试经理

    （2）测试经理确认缺陷，状态为激活，已确认，分配给开发人员

    （3）开发人员解决缺陷，状态为已解决，分配给测试人员

    （4）测试人员验证缺陷，若缺陷修复正确，关闭缺陷，状态为已关闭；若缺陷未修复正确，重新激活缺陷，状态为激活，分配给开发人员。

    bug生命周期的常见状态：
    1. New：新发现的bug指派给对应的开发人员；
    2. Open：开发确认bug，认为需要进行修改；
    3. Fixed：开发人员修改完成后，标识为已修复状态，等待测试人员进行测试；
    4. Rejected：开发认为不是bug，拒绝修改；
    5. Delay：开发人员延后修改，并给出理由；
    6. Closed：修改后的bug，经测试人员验证后关闭；
    7. Reopen：bug依然存在，重新打开bug；
    8. later：延期修改，下一个版本在修复。
    手工测试和自动化测试的优缺点：

    手工测试：

    • 灵活性高：比如我们查看产品列表时，发现图片加载缓慢，我们就可以对该部分再进行测试。
    • 发现非功能性问题：比如图片不够美观。
    • 效率比较低：需要我们点来点去。
    • 容易出错：完全依赖人工。

    自动化测试：

    • 效率高
    • 准确性高
    • 不能够完全替代手工测试
    软件测试的核心竞争力是什么？

    早发现问题和发现别人无法发现的问题。

    你了解的性能指标有哪些？

    QPS：系统每秒处理的查询请求数【查询数据】。

    TPS：系统每秒处理的事务数【"读 + 写" 一个完整的事务】。

    吞吐量：系统每秒处理的请求数。

    并发数：系统能够支持的最大并发数量。

    响应时间：从发送请求到返回响应的时间。

    错误率：一批请求中，错误请求所占的比例。

    bug优先级和严重程度的划分

    严重：引起崩溃的错误，如进程崩溃、进程停止执行，需要立即处理。

    高：主要功能发生的错误，引起数据丢失的缺陷。

    中：次要的功能和性能的缺陷。

    低：建议性错误或影响用户体验的缺陷。

    自动化测试关注指标

    我们可以从效率、覆盖率、质量三个方面来判断自动化测试框架设计的合理性，先从效率来说我们可以从测试用例的执行时间来进行衡量。从覆盖率方面来说，我们主要关注接口的覆盖率、测试用例的覆盖率以及业务场景的覆盖率。从质量方面来说，我们可以从自动化用例执行的一个成功率来进行衡量。

    自动化测试的覆盖率

    接口自动化：实现自动化测试的接口用例数量 / 总的接口用例数量，一般在95%左右。

    UI自动化：实现自动化的功能测试用例 / 总的功能测试用例，达到30%-40%就已经不错。

    接口测试和功能测试的区别

    接口测试：仅覆盖后端API。

    功能测试：覆盖前端操作 + 后端接口 + 数据库 + 第三方服务的全链路。

    如何设计接口测试用例
    1. 考虑接口的正确性，输入正确的参数，正确的请求方式，能够返回合理的结果，和数据库中的数据能够对应起来。
    2. 考虑接口的异常验证，包括请求方式不正确，参数类型、多填写参数、缺少必填参数、参数长度错误，能否返回对应的状态码。
    3. 考虑接口的业务逻辑，输入不同参数，能够返回对应的一个返回值。
    4. 考虑接口的安全验证。传输密码或用户信息等敏感数据时，是能够加密传输。

    接口测试用例：用例id，接口名称，URL地址、请求方式，输入参数，预期结果。

    Note：

    对于接口包含多个必填写参数以及非必填写参数的情况，应该如何测试？

    1. 必填写参数全部填写，全部正确的情况。
    2. 必填写参数全部填写，非必填写参数全部填写，全部正确的情况。
    3. 每个必填写参数都要测试为空、长度范围不正确、参数格式不正确的情况。
    4. 填写全部必填写参数，每个非必填写参数都要测试长度范围不正确、参数格式不正确的情况。
    5. 测试多填写额外的参数的情况。
    6. 测试填写不存在的参数的情况。
    如何定位bug是前端还是后端

    根据接口判断：

    1. 如果请求没发出或者url地址、请求方式、参数不正确（返回400、404、405状态码），一般为前端的问题。
    2. 如果url、请求方式、参数都正确，响应数据不正确或者没有响应，为后端bug。
    3. 后端返回了响应也是正确的，但是前端没有正确显示，一般就是前端问题

    根据日志判断：

    1. 根据日志记录的错误信息来判断。

    Note：

    问题的排查一般先定位是前端的问题还是后端的问题，定位后再根据日志找到错误。

    集成测试的主要方法：
    1. 非渐进式集成：大爆炸集成

    概念：对单个模块进行单元测试，单元测试完毕后，集成到一起，进行整体的测试。

    好处在于操作简单，坏处在于一旦出现问题，很难进行精确定位；而且无法保证测试用例的覆盖度。

    1. 渐进式集成

    渐进式集成主要分为自顶向下的集成、自底向上的集成以及混合式集成（三明治集成），思想主要是逐步集成模块，边集成边测试，属于一种单元测试和集成测试混合在一起的测试方法。

    （1）自顶向下的集成

    从主控模块开始，沿着层次结构向下集成。

    操作步骤：使用桩模块（固定返回值）来替代尚未开发完毕的底层模块，不断使用真实模块来替代桩模块，直到所有模块集成完毕。

    优点：能够尽早发现高层设计缺陷。

    缺点：前期需要开发大量的桩模块，前期工作量较大；底层关键功能验证较晚。

    （2）自底向上的集成

    从系统底层模块开始不断向上集成。

    操作步骤：编写模拟驱动模块来调用底层模块，不断用真实模块来替代驱动模块，直到所有测试完毕。

    优点：可以优先验证底层模块，保证基础。驱动模块开发比较简单。

    缺点：高层的主控模块问题发现较晚。

    （3）混合式集成（如：三明治集成）

    结合自底向上的集成策略与自顶向下的集成策略，通常将系统分为三层：

    目标层：当前需要测试的层次；

    目标层以上：自底向上的集成；

    目标层以下：自顶向下的集成。

    列表、元组、字典和集合的区别【下面是以元组核心来说】

    列表（list）是可变有序序列，支持索引和增删改；字典（dict）是可变无序键值对集合，通过键访问；元组（tuple）是不可変有序序列，支持索引但不可修改，相比于列表，占用内存少，查询速度快【元组的地址连续，列表因为动态扩容，地址可能不连续】；集合（set）是可变无序唯一元素集合，用于去重。

    字典：（1）可以用来存储配置信息；（2）可以用来当作计数器。

    字典的键和值可以由哪些充当？

    字典的键必须是不可变数据类型，数字类型（当修改值时，相当于创建一个新的值，然后让变量指向当前值）、字符串类型、布尔类型、元组类型、None。字典的值可以是任意类型。

    根据多种输入数据的组合情况进行测试用例设计。用于查询、搜索等场景。正交表行数n = k条件数 * （m取值数 - 1）+1，如果输入数据的取值数不同，那么分别计算然后相加。根据正交表行数找到正交表，根据正交表来设计测试用例，或者可以使用工具AllPairs。【判定表法主要聚焦于输入条件、正交表法主要聚焦于多种数据的组合情况】。

    根据业务流程来设计测试用例，采用流程图的方式，包含基本流以及备用流。基本流只有一个，包含一个起点和一个重点；通常指正常场景，即选择判断条件正确的路径。备用流包含多个，通常指异常场景或者备选场景。

    常见的白盒测试方法

    语分条，判路组

    语句覆盖、分支覆盖(判定覆盖)、条件覆盖、判定条件覆盖、组合覆盖以及路径覆盖。

    语句覆盖

    设计的测试用例，保证代码中的每条语句都至少执行一次。【弱覆盖，覆盖度低，只保证代码语句的覆盖】

    例子：

    if A and B then action1

    if C or D then action2

    测试用例：

    1. A = true、B = true、C = true
    分支覆盖（判定覆盖）

    设计的测试用例，要保证判断的所有结果【为真、为假的情况】都至少执行一次。

    测试用例：

    1. A = true、B = true、C = true、D = false
    2. A = true、B = false、C = false、D = false
    条件覆盖

    设计的测试用例，要保证每个条件的所有取值都至少执行一次。

    测试用例：

    1. A = true、B = true、C = true、D = true
    2. A = false、B = false、C = false、D = false
    判定条件覆盖

    相当于判定覆盖 + 条件覆盖，设计的测试用例要保证每个条件的所有取值都至少执行一次，还要保证每个判断的所有结果都至少执行一次。

    设计的测试用例

    条件覆盖满足：A = true、A = false、B = true、B = false、C = true、C = false、D = true、D = false；

    判定覆盖满足：A and B = true、A and B = false、C and D = true、C and D - false；

    判定条件覆盖对应的测试用例：

    1. A = true、B = true、C = true、D = true
    2. A = false、B = false、C = false、D = false
    组合覆盖

    设计的测试用例，要保证每个判断中各个条件取值的所有组合情况都至少执行一次。【强覆盖、覆盖度高、但是测试用例数量也多】

    设计的测试用例：

    1. A = true、B = true、C = true、D = true
    2. A = false、B = false、C = false、D = false
    3. A = true、B = false、C = true、D = false
    4. A = false、B = true、C = false、D = true
    路径覆盖

    设计的测试用例，要保证代码的每条可能存在的路径都要覆盖。【依据流程图】
