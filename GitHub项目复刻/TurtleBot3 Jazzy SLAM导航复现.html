    TurtleBot3 Jazzy：SLAM 与自主导航复现路线

    目标环境：Ubuntu 24.04 + ROS 2 Jazzy + Gazebo Harmonic。

    本项目的目标不是从零实现 SLAM 算法，而是完成并能解释一个真实的移动机器人软件链路：仿真、雷达与里程计、TF、建图、定位、路径规划、避障、日志与故障诊断。

    1. 项目目标与边界

    复现 TurtleBot3 Burger 在 Gazebo Harmonic 中的二维激光建图和自主导航：

    flowchart LR
    G["Gazebo Harmonic"] --> B["ros_gz 桥接"]
    B --> C["/clock /scan /odom"]
    C --> S["slam_toolbox 建图"]
    S --> M["地图 map.yaml / map.pgm"]
    M --> A["AMCL 定位"]
    A --> N["Nav2 规划与避障"]
    N --> V["/cmd_vel"]
    V --> G

    完成后应能做到：

    1. 启动 Burger 小车和 2D 雷达仿真。
    2. 用 slam_toolbox 建图并保存地图。
    3. 重启后在保存的地图中使用 AMCL 定位。
    4. 用 Nav2 发送目标点，完成全局规划、局部避障和到达。
    5. 使用自己编写的 C++ 诊断节点监控雷达、里程计和 TF。

    本笔记不包含真实机器人操作，也不宣称自主实现 SLAM 算法。

    2. 为什么选 Jazzy + Gazebo Harmonic

    ROS 2 Jazzy 对应 Ubuntu 24.04。TurtleBot3 的 jazzy 分支使用 ros_gz_sim、ros_gz_bridge 与 gz sim，因此不能直接套用 Humble + Gazebo Classic 的 gazebo_ros 教程。

    本项目固定以下版本组合，排错时首先确认没有混用版本：

    组件 固定选择
    操作系统 Ubuntu 24.04
    ROS 2 Jazzy
    仿真器 Gazebo Harmonic / gz sim
    小车 TurtleBot3 Burger，jazzy 分支
    建图 slam_toolbox
    定位与导航 Nav2 + AMCL
    自定义节点 C++ / rclcpp

    !!! warning "不要混用教程"

    不要把 Humble、Gazebo Classic、Ignition、Jazzy 的安装命令和 launch 文件混在同一个工作空间。遇到问题先执行 `echo $ROS_DISTRO`，结果必须是 `jazzy`。

    !!! warning "不要在 Conda 环境运行 ROS"

    运行 ROS 2 前执行 `conda deactivate`。Conda 的 Python、CMake 或动态库可能覆盖系统依赖，造成 `colcon build`、`rclpy` 或 Gazebo 插件异常。

    3. 上游仓库与工作空间

    上游源码：

    • turtlebot3（jazzy 分支）
    • turtlebot3_simulations（jazzy 分支）
    • slam_toolbox
    • Navigation2 / Nav2

    3.1 安装基础依赖

    以下命令默认 ROS 2 Jazzy 已安装。首次使用 rosdep 时，系统范围的 sudo rosdep init 只需要执行一次；若已初始化，则跳过该命令。

    sudo apt update
sudo apt install -y \
  git \
  python3-rosdep \
  python3-colcon-common-extensions \
  ros-jazzy-ros-gz \
  ros-jazzy-navigation2 \
  ros-jazzy-nav2-bringup \
  ros-jazzy-slam-toolbox

sudo rosdep init
rosdep update

    3.2 获取并构建 TurtleBot3 Jazzy 源码

    mkdir -p ~/tb3_jazzy_ws/src
cd ~/tb3_jazzy_ws/src

git clone -b jazzy https://github.com/ROBOTIS-GIT/turtlebot3.git
git clone -b jazzy https://github.com/ROBOTIS-GIT/turtlebot3_simulations.git

cd ~/tb3_jazzy_ws
source /opt/ros/jazzy/setup.bash
rosdep install --from-paths src --ignore-src -r -y
colcon build --symlink-install

    每个新终端都加载环境。不要把 source install/setup.bash 忘掉，否则系统可能启动到 apt 安装的旧包或找不到工作空间中的包。

    source /opt/ros/jazzy/setup.bash
source ~/tb3_jazzy_ws/install/setup.bash
export TURTLEBOT3_MODEL=burger

    3.3 构建后的最小检查

    echo $ROS_DISTRO
ros2 pkg prefix turtlebot3_gazebo
ros2 pkg prefix turtlebot3_navigation2
ros2 pkg prefix slam_toolbox
ros2 pkg prefix nav2_bringup

    期望：ROS_DISTRO 为 jazzy，四个包都能返回有效路径。

    4. 第一次完整跑通

    建议每个步骤使用独立终端，并在每个终端重新加载环境变量。

    终端 1：启动 Gazebo Harmonic 与 Burger

    source /opt/ros/jazzy/setup.bash
source ~/tb3_jazzy_ws/install/setup.bash
export TURTLEBOT3_MODEL=burger

ros2 launch turtlebot3_gazebo turtlebot3_world.launch.py

    该 Jazzy launch 文件通过 ros_gz_sim 启动 gz sim，不是 Gazebo Classic 的 gazebo 命令。

    终端 2：手动控制并检查传感器

    source /opt/ros/jazzy/setup.bash
source ~/tb3_jazzy_ws/install/setup.bash
export TURTLEBOT3_MODEL=burger

ros2 run turtlebot3_teleop teleop_keyboard

    另开终端检查关键话题：

    ros2 topic list | grep -E '^/(clock|scan|odom|tf|cmd_vel)$'
ros2 topic hz /scan
ros2 topic echo /odom --once

    终端 3：在线建图

    source /opt/ros/jazzy/setup.bash
source ~/tb3_jazzy_ws/install/setup.bash

ros2 launch slam_toolbox online_async_launch.py use_sim_time:=true

    回到键盘控制终端，让小车覆盖场景。移动时观察地图是否持续更新；地图严重重影时，先检查 TF 和里程计，不要立刻盲调 SLAM 参数。

    保存地图

    mkdir -p ~/tb3_jazzy_ws/maps
ros2 run nav2_map_server map_saver_cli -f ~/tb3_jazzy_ws/maps/tb3_world

    该命令应生成：

    ~/tb3_jazzy_ws/maps/tb3_world.pgm
~/tb3_jazzy_ws/maps/tb3_world.yaml

    终端 4：地图定位与自主导航

    停止在线建图节点，保留 Gazebo 仿真。然后启动 TurtleBot3 的 Nav2 包：

    source /opt/ros/jazzy/setup.bash
source ~/tb3_jazzy_ws/install/setup.bash
export TURTLEBOT3_MODEL=burger

ros2 launch turtlebot3_navigation2 navigation2.launch.py \
  use_sim_time:=true \
  map:=$HOME/tb3_jazzy_ws/maps/tb3_world.yaml

    在 RViz 中按顺序执行：

    1. 使用 2D Pose Estimate 给出机器人初始位置和朝向。
    2. 确认激光点云与地图障碍物重合。
    3. 使用 Nav2 Goal 设置目标点。
    4. 观察全局路径、局部轨迹和机器人最终状态。

    5. 必须理解的数据流与 TF

    TurtleBot3 Burger 的本体坐标系通常包含：

    map → odom → base_footprint → base_link → base_scan
    • base_footprint → base_link → base_scan：由机器人模型的固定/关节变换提供。
    • odom → base_footprint：来自轮式运动学或仿真里程计，会随时间累积漂移。
    • map → odom：建图或定位模块发布，用于修正里程计累计误差。
    • /scan：二维激光扫描，供 slam_toolbox、AMCL 和 costmap 使用。
    • /cmd_vel：Nav2 输出的速度指令，最终驱动仿真小车。
    • /clock：Gazebo 仿真时间；所有仿真节点必须使用 use_sim_time:=true。

    验证 TF：

    ros2 run tf2_ros tf2_echo odom base_footprint
ros2 run tf2_ros tf2_echo base_link base_scan
ros2 run tf2_tools view_frames

    view_frames 生成的 TF 图应只有一棵连通树。若 map、odom、base_footprint 分属不同树，建图或定位必然失败。

    6. 8 周学习路线

    第 1 周：环境与 ROS 图

    • 完成第 3、4 节的构建与首次建图。
    • 能解释 Node、Topic、Service、Action、Parameter、Launch 的区别。
    • 使用 ros2 node list、ros2 topic info -v、rqt_graph 查看实际通信关系。
    • 输出一张自己的系统数据流图和 TF 图。

    验收： 不看教程也能从空终端启动仿真、键盘控制和查看 /scan、/odom。

    第 2 周：坐标系、时间与里程计

    • 理解齐次变换、map、odom、base_footprint、base_scan 的职责。
    • 使用 tf2_echo 验证动态变换是否连续。
    • 对比 ros2 topic echo /clock --once 与各消息时间戳。
    • 人为关闭 use_sim_time，观察并记录 RViz、TF 或 Nav2 的异常，再恢复配置。

    验收： 能解释为什么“激光有数据但地图不更新”常常是时间或 TF 问题。

    第 3 周：SLAM 建图

    • 使用 slam_toolbox 完成同一场景的三次建图。
    • 对比慢速、快速、重复经过同一区域三种运动方式的地图质量。
    • 保存地图并记录建图范围、明显重影区域和可能原因。
    • 阅读 slam_toolbox 参数中与扫描、匹配、队列和更新频率有关的项；一次只改一个参数。

    验收： 保存的地图可用于后续定位；能解释 /scan、/odom、map → odom 与 OccupancyGrid 地图的关系。

    第 4 周：AMCL 与 Nav2

    • 在保存地图中启动 AMCL 和 Nav2。
    • 分别测试直线路径、窄通道、障碍物阻塞、目标不可达。
    • 记录全局路径、局部轨迹和最终结果。
    • 理解 global costmap、local costmap、planner、controller、recovery behavior 的职责。

    验收： 连续设置 10 个可达目标点，记录到达率、平均耗时和失败原因。

    第 5 周：系统化排障

    必须完成并记录以下三类故障：

    故障 现象 优先检查
    use_sim_time 不一致 TF 外推、RViz 数据停滞、导航不工作 /clock、节点参数、日志中的时间差
    TF 缺失或 frame 名不一致 No transform、地图不更新、costmap 无数据 view_frames、消息 frame_id、静态变换
    桥接或 costmap 配置错误 /scan 缺失、路径贴障碍、无法避障 ros2 topic hz /scan、量程、膨胀半径、传感器源

    每次排障按“现象 → 假设 → 检查命令 → 根因 → 修复 → 回归验证”记录，不接受只写“调参后好了”。

    验收： 给出三份故障记录，每份包含一条可复现命令或配置改动。

    第 6 周：C++ 诊断节点

    新建 tb3_diagnostics ROS 2 包，使用 C++ 和 rclcpp，不使用 Python 节点。

    节点最小职责：

    1. 用 rclcpp::SensorDataQoS() 订阅 /scan，统计雷达频率与消息时间戳延迟。
    2. 订阅 /odom，检测两帧间隔异常与不合理的位姿突变。
    3. 用 tf2_ros::Buffer 和 tf2_ros::TransformListener 定时检查 odom → base_footprint、base_link → base_scan 是否可查询。
    4. 使用节流日志输出异常；正常高频回调不刷屏。

    验收： 人为停止一个数据源或故意指定错误 frame 后，节点能在日志中给出可定位的告警。

    第 7 周：参数对比与量化评估

    • 固定地图、目标点和仿真初始位姿。
    • 仅修改一项参数，例如 costmap 膨胀半径、激光最大量程或控制器速度上限。
    • 记录成功率、到达时间、路径长度、碰撞/卡死次数。
    • 输出一张参数对比表，并说明保留某组参数的理由。

    验收： 至少完成两组可复现参数对比，结论能由数据支撑。

    第 8 周：作品集与面试准备

    • 整理工作空间 README：依赖、构建、启动顺序、地图、参数、故障与验证命令。
    • 保存一份 rosbag，录制“建图 → 保存 → 重启定位 → 导航”的 2 至 3 分钟演示视频。
    • 练习讲解：TF 树、map → odom 的意义、AMCL 和 SLAM 的区别、costmap 的作用、一次真实排障过程。

    验收： 在另一台同版本系统或全新工作空间中按 README 复现；不依赖临时口头补充。
